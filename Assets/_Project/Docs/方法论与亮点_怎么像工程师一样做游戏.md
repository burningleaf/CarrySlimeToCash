# 方法论与亮点：像工程师一样做一个游戏

> 这份文档写给"想学会这套做法"的你。
> 它不讲 Unity 按钮在哪，讲的是**遇到一个问题时，先做什么、后做什么、以及怎么知道自己没做错**。
> 所有例子都来自《带呆呆史莱姆越障换钱》这个真实项目，包括我踩过的坑 —— 坑比成功更有教学价值。

## 1. 第一原则：把"感觉"变成"能算的东西"

### 1.1 先看这个 demo 做了什么

大多数平台跳跃游戏的关卡好不好，靠**试玩感觉**。感觉这东西有三个致命问题：

1. **说不清** —— "这关有点拖"到底拖在哪？
2. **传不了** —— 你没法把感觉交给另一个人去调。
3. **测不出** —— 改了一个数字，是变好了还是变坏了？只能再玩一遍。

这个 demo 的核心设计决定，是把"时间和钱"合并成**同一种货币**：

```
最终售价 = 满格售价 × 血条剩余百分比 + Σ 拾取的金币

血条随时间往下掉（血条 = 2 × parTime 点，每点固定 5 元）：
  hpPerSecond = 1.0 点/秒         ← 掉血速度是常数，**与 parTime 无关**
  moneyPerHp  = 5 元/点           ← 1 点 = 1 秒 = 5 元
  barMax      = 10 × parTime      ← 满格 = 血条点数 × 每点单价
```

**这一步做完，整个游戏就"能算"了。**

因为现在：

- "绕路去捡这枚金币值不值？" → 金币 10 元 ÷ 5 元每秒 = **2 秒预算**。绕路 1.3 秒 → 值；绕路 2.6 秒 → 不值。**这是一个能算的题，不是一个感觉。**
- "我打得快还是慢？" → 秒数直接换算成钱，秒数就是分数。
- "这关设计得好不好？" → 冲刺路线赚 425 元，全收集路线赚 506 元，差 +19.1%。**这是一个能验收的数字。**（⏳ 现值：冲刺 **416 元** / 全收集 **496 元** / 差 **+19.2%** —— 2026-09-24 重定基线，见下。）

> ⚠ **口径更新（2026-09-23）**：收益差的分子已从"全收集"改为 **R\*（精确最优）**，当时 Level1 现值 **+19.5%**（三关 **+20.4% / +19.5% / +20.6%**）。
> ⏳ **再更新（2026-09-24 重定基线）**：净空进模型后四关现值为 **+18.2% / +19.2% / +16.3% / +18.0%**（Level1 = **+19.2%**），四关最短时间 **21.6 / 36.8 / 17.7 / 8.7 秒**，求解器自检 **46 项**（用例数会随新增用例增加，以 `2 求解与校验 → 求解器自检` 的实际输出为准；同一轮里先记的是 33 项，P5 之后是 46 项）。
> ⏳ **再更新（一次判据修正后）**：**Level3** 由 8.7 → **8.1 秒**、收益差 +18.0% → **+17.1%**（冲刺 556 → **560 元**）；自检 **46 → 67 项**（+T12 4 / T13 7 / T14 10）。四关现为 **21.6 / 36.8 / 17.7 / 8.1 秒**、**+18.2% / +19.2% / +16.3% / +17.1%**。
> 本文里的 `+19.1%` / `+19.7%` / `+19.4%` / `20.5s` / `35.0s` / `16.6s` 都是**当时口径**的历史数字（保留原貌）；最新定义见 `定案_收益公式与调参基准.md` §10，最新数值见 `项目进度_现状与下一步.md` §5。

### 1.2 为什么这是最关键的一步

因为它把一个**主观问题**（"这关好玩吗"）拆成了一个**客观问题**（"最优路线和次优路线的收益差是多少"）加上一个**主观问题**（"这个差值区间我喜不喜欢"）。

拆开之后：

- 客观部分可以**测量**、可以**回归**、可以交给程序去算。
- 主观部分只剩一个数字要你拍板：**收益差多少才算"值得纠结"？** 这个 demo 的答案是 15%~35%（§5.3 会讲为什么）。

**可迁移的做法**：

> 设计任何一个系统时，先问自己："这个系统里，玩家做的两个选择，我能不能用一个数比较它们？"
> 如果只能比较"哪个更好玩"，那这个系统就永远只能靠感觉调。
> 如果能比较"哪个多赚 80 元"，那它就能被优化、被测量、被自动化。

## 2. 我的开发循环（七步）

这是我在这个项目里实际用的循环。每一步都有这个项目里的真实例子。

### 第 0 步：把验收标准**先写下来**

不是"做完再说好不好"，而是**动手之前**就写清楚"什么叫做完了"。

真实例子（进度文档 §5.2 的原表）：

| 步骤 | 做什么 | 验收标准 |
|---|---|---|
| 第 3 步 | P2 求解器 | **对 Level1 输出报告；对人为造的"逃课图"能报出来** |
| 第 4 步 | 放一关机关进去 | **一关里各用一次，全部正常联动** |

注意这两条验收标准都**可以被证伪**。"求解器能算最短时间"不是验收标准 —— 算出来的可能是错的。
"对人为造的逃课图能报出来"才是：它要求你**造一个已知答案的测试**。

**第 4 步的验收标准最后变成了 59 项断言**，全过才算数。如果当初写的是"机关能联动"，那我会看一眼场景觉得"引用都拖上了，应该行" —— 然后交付一堆跑起来全是 bug 的机关。

> **可迁移的做法**：验收标准要写成"能观测到的现象"，不能写成"功能存在"。
> ❌ "实现了压力板" → ✅ "站在压力板上，门会打开；走开之后门保持打开"
> ❌ "关卡能通关" → ✅ "6 格坑过不去，4 格坑过得去"

### 第 1 步：找出**最危险**的那件事，先做它

不是"从简单的开始"，是"从最可能炸的开始"。

第 4 步要放的五类机关（压力板 / 移动平台 / 门 / 敌人 / 检查点），代码是**很早以前就写完的** —— 但**一次都没跑过**。

这是全身风险最高的地方。所以进度文档里明确写了：

> 这五类代码从没跑过，风险最高，**越早炸越好**。

结果真的炸了两个：

1. 移动平台的路点被挂成了平台的子物体 → **平台会一路飞出去停不下来**
2. 压力板的默认掩码把移动平台过滤掉了 → **"平台压板"这种机关永远触发不了**

这两个 bug 如果留到第 5 步（美术音效）之后才发现，就要在"画面已经好看、音效已经配好"的版本上动核心逻辑 —— 修起来贵十倍，而且容易把好看的部分一起修坏。

> **可迁移的做法**：列出所有模块，给每个标"从写完到现在跑过几次"。
> **跑过 0 次的模块，不管它多简单，都是最高风险。** 先跑它。

### 第 2 步：先做**便宜的探针**，再做贵的东西

第 4 步的关键难题是：**"联动"是运行时行为，怎么自动验证？**

我本来打算用 Unity 的 Play 模式跑无头测试。但在投入两天写测试之前，我先写了一个 60 行的探针：
进 Play 模式 → 数 60 帧 → 报告 Update/FixedUpdate 各跑了多少次。

**探针跑了 400 秒没完成 —— 批处理模式下进不了 Play 模式。**

于是立刻换方案（自己搭无头游戏循环，§4.3）。如果我直接开始写那个 Play 模式测试，会在两天后才发现路走不通。

> **可迁移的做法**：任何"不确定能不能行"的技术前提，先用最小的代码验证它。
> 探针的价值不在于它测出了什么，而在于**它便宜到可以随手扔掉**。

### 第 3 步：在**数据**里做，不在场景里做

这个 demo 的三关不是"在 Unity 里摆出来的"，是这么来的：

```
LevelData（JSON 文本）  ──LevelBuilder.Build()──▶  场景
       ↑                                              │
       └──────────ExportScene() 导出回来───────────────┘
```

**JSON 是真相源，场景是它的投影。**

为什么这么做？因为场景文件是二进制式的、几十万字节、没法 diff、没法手改、没法生成。而 JSON：

- 能 diff（"这次改动到底动了哪几个数"一眼看清）
- 能 grep（"哪几关用了 PressurePlate？"一条命令）
- 能生成（地图生成器就是把玩家拖出来的东西写成这个 JSON）—— **这是第 6 步地图生成器的全部技术前提**

真实数据：`Level1.json` **9.4 KB**，对应的 `Level1.unity` **340 KB** —— 36 倍的差距，而且一个是可读的，一个是不可读的。

而且数据一改，场景能**一键重建**：

```
Tools → 呆呆史莱姆 → 1 关卡数据 → 从 JSON 重建场景   （用 JSON 重建场景）
Tools → 呆呆史莱姆 → 1 关卡数据 → 往返一致性检查      （验证重建前后一模一样）
```

> **可迁移的做法**：把"内容"和"引擎资产"分开。
> 内容用文本格式（JSON/CSV/YAML）存，写一个生成器把文本变成引擎里的东西，再写一个导出器把引擎里的东西变回文本。
> 一旦有了这两个方向，你就能**生成内容**、**批量改内容**、**用程序检查内容**。

### 第 4 步：给每一种"算出来的结论"配一个**体检仪**

这是这个项目里我最满意的工程决定。

求解器能算出"Level1 最短 **36.8** 秒"（⏳ 2026-09-23 那批是 35.0 秒；2026-09-24 净空进模型后重定为 **36.8** 秒）。问题是：**这个数字凭什么是 36.8 而不是 20 或 60？**

于是有了四层体检：

| 层 | 体检仪 | 抓什么 |
|---|---|---|
| 1 | **直线下界自检** | 任何走法都不可能比"直线跑过去"更快。求解结果 36.8s < 下界 30.3s 就说明**算错了**，立刻暴露 |
| 2 | **求解器自检**（**14 组 / 67 项**） | 14 个**答案能手算**的迷你关卡（T1~T14），把结果钉死 |
| 3 | **逐动作路线明细** | 把最优路线拆成 `0.64s 落 Ground_D(x92@y0) → PitFloor(x92@y-6)`，每一行都能肉眼核对 |
| 4 | **三态「谜题可解」判据** | 通关条件是"**史莱姆**进终点" ⇒ **空手可达证明不了能过**：① 空手 ② 携带 ③ 史莱姆单独 ④ 跟跳，四种口径并列 |

**第 2 层是抓 bug 最狠的。** 因为求解器算错了，报告看起来**一模一样地合理**。

第 2 层具体长这样（`LevelSolver.cs` 的 `BatchSolverSelfTest`）：

| 用例 | 手算答案 | 验证什么 |
|---|---|---|
| T1 直路 18 格 | 2.77s | 基本计时 |
| T2 四格坑 | 3.67s / 可达 | 空手跳最远 5.87 格 |
| T3 六格坑 | **不可达** | 逃课图必须能报出来 |
| T4 5 格高墙 + 台阶 | 有台阶可达 / 抽掉台阶不可达 | 墙要切断走道 |
| T5 顺路币 / 远币 | 0.0s / 8.0s | 金币取舍公式 |
| T6 悬空台金币 | 1.01s | 回程必须按**掉落**计价 |
| T7 顺路币 + 绕远币（R\*） | **R\* = 104 元 / 只捡 1 枚 / 耗时 1.23s** | 收益差分子换成 R\*：掩码枚举挑出"捡哪几枚最赚" |
| T8 走道 + 低天花板（净空） | **翻越 6.9270s / 直走 5.8462s —— 两条都不可行** | 净空进模型：矮到钻不过去 = 该段**不可通行**，不许再按"钻得过去"计价 |
| T9 「全收集」升级成可行解 | **全收集精确 9.2308s / 74 元；R\* 1.2308s / 104 元** | 「全收集」必须是**真实存在的路线**（用可收集掩码算耗时），且 `R* ≥ 全收集` 恒成立 |
| T10 只有空手能过（携带） | **空手可达 2.9850s；携带 ❌（第一卡 dy=+2.25）、史莱姆单独 ❌、跟跳 ✅** | 携带跳高降到 1.8 ⇒ 2.2 格台阶**连跳边都不生成**（携带包络真的进了模型） |
| T11 史莱姆通道（矮通道 / 窄槽） | **T11a 玩家翻越 5.5424s vs 史莱姆直穿 4.8333s；T11b 0.75 格窄槽两边都钻不过去** | 「玩家过不去、史莱姆过得去」这个方向成立；反方向**做不出来**（史莱姆 0.9 比玩家 1.2 矮 + 0.25 格网格） |

这套断言（**当时是 15 项，现在已是 14 组 / 67 项** —— 2026-09-23 加了 T7 的 5 项 R\* 断言与 T8 的 5 项净空断言，2026-09-24 又加了 T9 的 8 项「全收集 = 可行解」断言与 T10 / T11 两组「携带包络 + 史莱姆通道」断言）**当场抓出了 4 个我自己写的、会让报告"看着合理但是错的"bug**（§4.2 详讲）。⚠ 用例数会随新增用例增加，**引用时以 `2 求解与校验 → 求解器自检` 的实际输出为准**。

**第 4 层是我后来补上的，它治的是"体检仪本身问错了问题"**：

- 通关条件是「**史莱姆**进终点」，可前面三层的默认口径都是"**空手玩家**" ⇒ 出来的"可达 ✅"**逻辑上不构成"这关能过"**。
- 补上第 4 层后，工具自己给出**反证**：**五关的"携带态"都到不了终点**（第一个卡住的跳：Level0 dy=+2.5 / Level1 +2.0 / Level2 +3.0 / Level3 +2.0 / LevelMech +2.5），**"史莱姆单独"也到不了**（它自己**不会跳**），**只有"跟跳"能到**。
- ⇒ 结论不再是"我觉得要配合"，而是**"必须放下 → 玩家先跳 → 引它跟跳"**，而且这条结论是**工具算出来的**。
- 顺带白捡一张设计地图：**史莱姆钻得过去、玩家钻不过去**的三处通道（Level0 `Tunnel_1` x[78,92]、Level1 竖井底与东侧两段、Level2 引导墙下 `Ground_Right` x[24,32]，净空 1.0：史莱姆 0.9 / 玩家 1.2）—— 工具自己就把"必须让史莱姆单独走"的谜题资源点出来了。
- ⛔ **主口径没变**：基线仍是**空手**（21.6 / 36.8 / 17.7 / 8.1 秒）。把那三套数字当主口径会把整个基线换掉（例如 `LevelMech` 8.7 → **108.3** 秒）—— **并列输出，不要覆盖**。
- ⚠ **边界**：机关（门 / 压板 / 移动平台 / 敌人）**仍不在模型里** —— 报表那三节（三态 / 携带可达性 / 史莱姆通道）**末尾各自都带同一句硬提醒**：**⛔ 机关不在模型里，最终以真人试玩为准。**

> **可迁移的做法**：任何"算出来"的东西，都要有至少一个**独立来源**的验证。
> 最好的独立来源是"能手算的答案" —— 因为它跟你的代码没有任何共同假设，不会跟你一起错。

> **追加的三条可迁移结论（2026-09-24 收口）**：
>
> ① **视觉质量也能变成"可证伪的硬规则 + 机器自检"** —— 一句"元素互相重叠看不清"先被量成数（圆键帽直径占了画布的 **34.4%**），再立成"三带一缝 + 10 条硬规则"，每张图**写盘前**跑一次读真实不透明像素包围盒的自检（`成功 20 / 占比告警 0 / 防重叠不过 0 / 失败 0`）。⚠ 规则里必须留一条**"⛔ 不许把元素缩小硬塞"**的禁令，否则最省事的做法会绕过规则。
> ② **"预检台"必须被真管线背书，才有资格做变更前预检** —— 离屏内存渲染只有在与真产物**逐像素差异 0**（20/20 张；两条缝各 0 像素；24 个圆键帽 17×17 的圆心 / 字形逐点一致）之后才可信；否则它只是一个**长得像**的替身，预检给出的安全感是假的。
> ③ **等价变换要"逐格验算 + 全量回归"，只做一半不算证明** —— 经济口径那次重参数化（血条 `2 × parTime` 点 / 每点 5 元 / 掉血 1.0 点/秒 ⇒ 每秒恒掉 5 元，核心心算 **1 点 = 1 秒 = 5 元**）先用代数证明与旧口径**逐格等价**（旧 `(1 − t/2P) × 100 × (P/10)` ≡ 新 `(1 − t/2P) × 2P × 5` = `10P − 5t`），再拿**全量回归**证明"钱与手感零变化"。

### 第 5 步：改产品代码要**最小化**，改完必须跑**回归**

第 4 步我只改了两处产品代码（都在 `LevelBuilder.cs`）：

1. 移动平台的路点从"平台的子物体"改成"挂在平台父节点上"
2. 压力板默认掩码加上 `MovingPlatform` 和 `Enemy`

改完立刻跑回归：

```
求解器自检          15/15 全过
三关求解数字         20.5s / 35.0s / 16.6s  ← 和改之前一字不差
三关往返一致性       3/3 一致
```

**"一字不差"就是回归通过的定义。** 如果数字变了，要么是我改错了，要么是我无意中改了关卡 —— 两种都必须查清楚才能继续。

> ⏳ **2026-09-24 重定基线**：上面那个代码块是**当时**的读数（自检 15/15、三关 20.5 / 35.0 / 16.6 秒、往返 3/3）。同一套回归现在跑出来是：自检 **46/46**（P5 之后；同一轮里先记的是 33/33） · 四关最短时间 **21.6 / 36.8 / 17.7 / 8.7 秒** · 往返 **4/4**。数字变了，但这次**是"求解器变准了"（净空进模型），不是关卡被改动** ⇒ 判据也随之升级：从"三关数字一字不差"变成"**四关数字与《定案_收益公式与调参基准.md》§10.5 的基线一致**"。

> **可迁移的做法**：动手改之前，先把"改完之后应该还是什么样"记下来。
> 没有回归基准的改动，等于闭着眼睛做手术。

## 3. 十条我认为最值钱的工程习惯

### ① 警惕"静默收敛到默认值"

**最危险的 bug 不是崩溃，是不崩溃。**

真实事故：导出器漏读字段。它不会报错 —— 它会用代码里的默认值填上，然后一切运行正常，只是数据**悄悄变了**。改三次才被发现，因为前两次的表现是"重开游戏发现金币位置不对"。

**对策**：任何"双向转换"都要有**逐行比对**，不能只验证"能转回来"。因为漏字段的转换是**自洽**的：丢字段 → 用默认值 → 再导出 → 还是默认值 → 往返检查通过 ✅。

这个项目的 `BatchRoundTripAll` 专门加了这一步：**磁盘 JSON vs 场景导出结果**，而不是只比"导出→重建→导出"。

### ② 让下界成为你的报警器

求解器每次报告都会带上"直线下界"：

```
【自检】直线下界 30.3s（水平距离 ÷ 移速）｜ 求解结果 36.8s  ✅ 合理
```

任何最短路算法出错（比如误把段内走路算成免费），结果会**小于下界** —— 这是物理上不可能的。一个廉价的、不可能被绕过的报警器。

**可迁移**：给每个"算出来的数"找一个**理论上不可能突破的边界**。算出来的越界了，不用看细节，直接断定有 bug。

### ③ 把手算的答案变成测试

不要写"我觉得这个结果对"。写"我知道这个结果必须等于 3.67，误差不超过 0.08"。

这个项目的 T1~T6 全部是**手算出来的**：`9/6.5 + 0.903 + 9/6.5 = 3.67`。手算过程写在注释里，所以将来改坏了，看注释就知道原本应该是什么。

### ④ 知道你的模型**看不见什么**，并且**说出来**

求解器是"脚底可站立面"模型 —— 它**天生看不见头顶**。

于是它会把一条净空只有 1.0 格（玩家身高 1.0）的矮通道算成"直接走过去"，报出的时间偏乐观。

**它没有假装自己看得见。** 而是专门加了一个纯几何的【净空检查】段落：

```
【净空检查】玩家碰撞盒高 1 格（净空低于它 = 玩家钻不过去）
    Ground_E+Ground_F+Ground_G  x[146,176] 净空 1  压顶=Tunnel_1  玩家钻不过去 ❌
    ⚠ 求解器是「脚底可站立面」模型，看不见头顶：
      上面这些路段的最短时间是按**直接走过去**算的，偏乐观；钻不过去时真实耗时更多。
```

**一个诚实标注了自己适用范围的工具，比一个假装全能的工具值钱十倍。**

顺带一提，这个净空检查第一次写完时是**错的**：它用的判据是"净空 < 玩家身高"，而矮通道的净空**恰好等于**玩家身高 1.0 —— 差一点点就漏掉了。改成 `<= 身高 + 0.05` 才抓到。

### ⑤ 一个模块"写完"和"跑过"之间隔着一条河

五类机关的代码早就写完了。文档里甚至写着"压住即激活目标（移动平台、门、机关）"。

**但它一次都没跑过。** 一跑就发现：代码里的说明和实际能不能跑通是两件事。

具体是：`PressurePlate` 的注释写着"玩家 / 史莱姆 / 怪物 / **移动平台**压住即激活"，碰撞矩阵里 `MovingPlatform × TriggerZone` 也确实是开的 —— 但 `LevelBuilder` 里那个默认掩码 `GetMask("Player","Slime","CarriedSlime")` 把它**过滤掉了**。

**代码注释描述的是意图，掩码决定的是现实。** 两者不一致时，现实赢。

### ⑥ 先证明前提，再写代码

第 4 步的探针（§2 第 2 步）花了 20 分钟，省了两天。

类似的还有：在写联动测试之前，先派一个子代理去**逐位解码** `Physics2DSettings.asset` 的碰撞矩阵，确认"玩家↔敌人""玩家↔门""移动平台↔触发区"这些对到底开没开。

**结果非常有价值**，其中几条反直觉的：

| 结论 | 影响 |
|---|---|
| 玩家 ↔ 拾取物 = **关** | **只有史莱姆能捡金币**，玩家碰到不触发。这是故意的，不是 bug |
| 门 ↔ 地面 = **关** | 门必须是静态物体，不能给它加刚体 |
| 移动平台 ↔ 移动平台 = **关** | 平台之间互相穿过 |
| 默认层 ←→ **任何层都不碰** | 新物体忘改层就会**静默穿地掉下去** ⚠ |

如果我猜"玩家肯定能捡金币"，我会做出一个完全错的关卡。

### ⑦ 单位混乱是隐形杀手

这个项目统一规定：**1 格 = 1 Unity 单位，地形顶点统一 y = 0**。

因为统一，才可能有这些简单公式：

```
跳跃能跨多远 = 滞空时间 × 移速
上升时间 t1 = √(2 × 跳高 / 重力)
下落时间 t2 = √(2 × (跳高 − 高度差) / 重力)
```

代入这个 demo 的数值（重力 = 9.81 × 3 = 29.43）：

| 动作 | 跳高 | 滞空 | 水平能跨 |
|---|---|---|---|
| 空手跳 | 3.0 | 0.903s | **5.87 格** |
| 抱着史莱姆跳 | 1.8 | 0.700s | 2.45 格 |

于是"这个坑跳得过去吗"变成一个**查表问题**：

- 3 格坑 → 5.87 > 3，跳得过去
- 4 格坑 → 跳得过去（实测 3.67s）
- 6 格坑 → 5.87 < 6，**跳不过去**（实测"不可达"，这就是关卡的硬约束）

**5.87 这个数字是推导出来的，不是试出来的。** 所有关卡尺寸都按它设计，所以不会出现"这关不知怎么就过不去"。

> **可迁移的做法**：先定能力参数，再推算出"能跨多远/能跳多高"，最后用这个数去设计障碍。
> 反过来（先摆障碍再试能不能过）会做出大量"差一点点跳不过去"的挫败关卡。

### ⑧ 尽量少改已经确认好的东西

第 4 步要放机关。把机关塞进 Level1 是"最省事"的做法 —— 因为 Level1 刚重做完，地形现成。

但我新建了一关 `LevelMech`。理由：

> 那三关刚刚确认好（第 2 步重做 + 求解器体检过）。单独一关可以放开手做，也正好当"五类机关各用一次"的验收现场。

**代价**：多花一点时间建场景。
**收益**：机关 bug 和关卡 bug 不会互相污染，排查范围减半；而且 Level1 的求解报告（**36.8s / +19.2%**；⏳ 当时是 35.0s / +19.1%）始终是一个**没有被搅动的基准**。

### ⑨ 报错要报"差异"，不要只报"失败"

看这个报错的质量：

```
⚠ Level1 的 JSON 与场景不一致 —— 导出器可能漏读了字段
    JSON：T Ground|Ceiling|472,6|96,6|-
    场景：T Ground|Ceiling|476,6|96,6|-
    JSON：T Ground|Pillar_2|304,6|8,5|-
    场景：T Ground|Pillar_2|256,2|8,5|-
    ...
```

它不但说了"不一致"，还把**具体哪一行、哪个字段、两个值分别是什么**都列出来了。

**结果是：我 30 秒就定位到了问题**（场景里多出一个 `Pillar_2`，位置在 x64..66、贴地悬空 0.5），而不是花两小时去猜。

对比一下"检查失败 ❌"这种报错 —— 它让你从零开始查。

### ⑩ 把"体检"做成一条命令

所有的检查都做成了命令行入口：

```powershell
Unity.exe -batchmode -quit -projectPath <工程> -executeMethod LevelSolver.BatchSolverSelfTest
Unity.exe -batchmode -quit -projectPath <工程> -executeMethod LevelSolver.BatchSolveAll
Unity.exe -batchmode -quit -projectPath <工程> -executeMethod LevelDataWindow.BatchRoundTripAll

```

**为什么重要**：因为"要检查"变成了一件**成本接近零**的事，所以我每次都真的会检查。

如果检查需要"打开 Unity → 点开某个场景 → 点菜单 → 看 Console → 手动对比"，那我改三次代码可能只检查一次。

> **可迁移的做法**：把重复的检查自动化到"一条命令"的程度。
> 自动化的价值不在于省时间，在于**把"要不要检查"从一个决策变成一个习惯**。

## 4. 技术亮点精讲

### 4.1 【最核心】可站立面站点图求解器

这是整个 demo 技术上最有意思的部分。

#### 要解决的问题

给一个关卡，算出：
- 玩家能不能走到终点？
- 最短要多久？
- 每一枚金币"绕路去拿"要额外花几秒？值不值？
- 哪个障碍移掉之后可以让玩家抄近路（= 逃课）？

**约束条件**（这个项目明确禁止的）：不能用 `CharacterController2D`、不能生成寻路 / A* / NavMesh 相关代码。

所以不能用格子 A*。

#### 三代演进（这一段是全文最值得看的）

**第一代：一个可站立面 = 一个节点**

最直觉的做法。把地面、平台、台阶都变成节点，能互相跳过去就连边，边权 = 跳跃耗时。

**结果：Level1 报出 7.0 秒，而直线下界是 24.0 秒。**

原因：**段内走路是免费的**。Level1 有一段 47 格长的地面（`Ground_D`，x45~92），玩家在这段地面上从 x45 走到 x92 需要 7 秒多 —— 但在模型里，"到达 Ground_D"就等于"到达 Ground_D 上的任何一点"。

于是求解器认为：跳上这条长地面 = 到达终点附近 = 7 秒。

> **教训**：模型的**粒度**决定了结果的对错。粒度太粗时，误差不是"差一点"，是"差 3 倍"。

**第二代：一个可站立面 = 两端两个节点**

修法很自然：段内走路要收费，所以给每段取两端两个节点，段内连一条"走"边，费用 = 段长 ÷ 移速。

**结果：Level1 报"不可达"，而它明明是能通关的。**

原因：**起跳被绑死在端点上了**。

Level1 的竖井里，`Step_1`（x104~108）**嵌在** `PitFloor`（x92~114）内部。玩家实际是在台阶正下方往上跳 —— 水平距离 `dx = 0`，一个**垂直跳**。

但端点组合的最小水平距离是 6 格（92 到 104 或 108 到 114），而 `MaxJumpDx` 是 4.63 格。**6 > 4.63 → 连不上 → 报不可达。**

> **教训**：修 bug 时容易把模型推向另一个极端。"太粗"的对面不是"刚好"，往往是"太细/太死"。

**第三代（最终）：站点法**

正确做法是：**每一段上取若干"站点"，而不是固定取端点。**

站点从哪来？

```
每段上的站点 = 段的两端
             + 出生点的 x
             + 终点的 x
             + 每一枚金币的 x
             + 与每一个其他段的"最接近点"
```

- **段内**：相邻站点之间连"走"边，费用 = Δx ÷ 移速（段内走路要花钱 ✅）
- **跨段**：只在两段的**最接近点对**之间连边（垂直跳 dx=0 自然成立 ✅）

`Level1` 现在的规模（实测）：**22 段 / 72 站点 / 188 条边**（图节点 86 = 72 站点 + 12 枚金币 + 出生点 + 终点）。用 Dijkstra 算两次最短路（正向一次、反向一次），0.29 秒出结果。

**为什么"与所有其他段的最接近点"这一条是关键**：它让"从这段的哪个位置能跳到那段"变成一个**自动推导**出来的东西，而不是写死的位置。加一个新平台，站点自动出现在正确的地方。

#### 顺带白捡的好处

一旦图建好了，"金币绕路代价"就是一次减法：

```
绕路代价 = 起点→金币的最短时间 + 金币→终点的最短时间 − 起点→终点的最短时间
```

- `起点→金币` 用**正向图**跑一次 Dijkstra，得到所有节点的距离
- `金币→终点` 用**反向图**跑一次 Dijkstra
- 相加减去总时间，就是"专门为这枚金币多花的秒数"

**这是"把问题建模对"的典型回报**：你花力气想清楚了模型，之后很多问题都变成同一张图上的查询。

### 4.2 四个"看着合理但是错的"bug

这 4 个 bug 全是求解器自检抓出来的。它们共同的特征是：**报告看起来完全正常**。

#### Bug 1：掉落被按"跳"计价

代码原本长这样：

```csharp
// 跳过去 / 跳上去
float maxDx = MaxJumpDx(dy, ab);
if (maxDx > 0f && dx <= maxDx)
{
    g.Add(na, nb, JumpTime(dy, ab), "跳");
    continue;          // ← 就是这一行
}

// 直接走下去（不跳，靠重力）
if (dy < -0.5f) { ... }
```

那个 `continue` 的意思是：**只要连上了"跳"边，就不再考虑"落"边**。

后果：从地面掉进 6 格深的井里 ——

- 重力下落：`√(2×6/29.43) = 0.64 秒`
- 但"跳过去"的计价：`1.23 秒`

于是求解器认为"掉进井里"要 1.23 秒，它算出来的最优路线变成：**先爬上一根柱子，再从柱子上跳进井里**。

报告输出（当时的真实结果）：

```
0.58s  跳  Ground_D(x85@y0)     → Pillar_4(x85@y2.75)     ← 莫名其妙爬柱子
1.35s  跳  Pillar_4(x86@y2.75)  → PitFloor(x92@y-6)
```

**它宁可绕路爬柱子，也不肯直接走进坑里。** 而 `35.4s` 这个数字看起来完全合理。

修法：不要 `continue`，两条边都连上，让 Dijkstra 自己选便宜的。

```csharp
// ⚠ 这里**不能**因为上面已经连了"跳"边就 continue：
//    从地面掉进 6 格深的井里，重力下落 0.64s，而"跳过去"要 1.23s。
if (dy < -0.5f)
{
    float fallT = Mathf.Sqrt(2f * (-dy) / ab.Gravity);
    if (dx <= fallT * ab.moveSpeed) g.Add(na, nb, fallT, "落");
}
```

修完之后路线变成 `Ground_D(x92@y0) → 落 → PitFloor(x92@y-6)`，0.64 秒，和手算一致。

> **教训**：优化代码里每一个 `continue` / `break` / `return`，都在说"剩下的情况不可能更好"。
> **这句话必须能证明。** 证明不了，就是 bug。

#### Bug 2：立在地上的墙**不存在**

`BuildSegments` 会把"同一高度、水平相接的地面"合并成一整段 —— 这本身是对的（一条连续走道）。

但它带来一个隐藏后果：**一块立在地面中间的墙，不会把这段地面切断**。

于是模型认为：地面还是一整条，玩家可以从墙的位置**直接走过去**。

自检用例 T4 就是拿这个钉出来的：

```
T4 场景：地面 0..20，一堵 5 格高的墙立在 x10..11，旁边 x8..9.5 有个 2.5 格高的台阶

预期：借台阶翻过墙 → 可达
      抽掉台阶 → 翻不过去 → 不可达
实际：抽掉台阶后**依然可达** ❌   ← 因为模型认为玩家能穿墙
```

修法分两步：

1. **墙要切断走道**：找底面接着这条走道（不是悬空的）、顶面高到迈不上去（超过 `stepHeight`）的方块，把它的 x 区间从走道里**挖掉**
2. **跳跃要检查中间有没有东西**：光切断还不够 —— 切断后的两截地面自己又会连出一条"跨越墙"的跳边。所以要检查两点之间地面上的最高障碍，如果它高过跳跃顶点，这一跳就是撞墙，不连边

```csharp
float topBetween = HighestTopBetween(d, ignore, ta, tb);
float apex = Mathf.Min(a.y, b.y) + ab.jumpHeight - 0.05f;
bool clearJump = topBetween <= apex;
```

同理，**下落**也要检查：下落途中如果半空有平台，人会落在上面，所以"直达地面"这条边不成立。

> **教训**：一个模型如果只描述"能站在什么上面"，那它就默认"除了地面之外什么都不存在"。
> 障碍物要么进模型，要么模型会假装它不存在。

#### Bug 3：反向图不同步 —— 金币绕路代价**正好翻倍**

这个 bug 最隐蔽。看代码：

```csharp
public void Add(int from, int to, float cost, string kind)
{
    foreach (Edge e in fwd[from])
        if (e.to == to) { if (cost < e.cost) { e.cost = cost; e.kind = kind; } return; }
    fwd[from].Add(new Edge { to = to, cost = cost, kind = kind });
    rev[to].Add(new Edge { to = from, cost = cost, kind = kind });
}
```

"同一条边只留更快的" —— 当一条更便宜的边到来时，它更新了 `fwd`。

**但忘了更新 `rev` 里对应的那条。**

后果：`toGoal`（"从某点走到终点要多久"）是用**反向图**跑的 Dijkstra。而反向图里，从柱子到地面的代价一直是**旧的贵价**：

| | 正确 | 反向图里的陈旧值 |
|---|---|---|
| 从 2.75 格高的柱子**掉下来** | 0.43s | **0.89s**（跳下来的价） |

于是所有需要"从高处下来"的金币，绕路代价都被系统性高估 —— **柱顶金币的绕路代价正好翻倍**（1.3s 变成 2.6s）。

后果有多严重？它会**改变设计结论**：

- 正确：`C_Pillar1` 绕路 1.3s < 预算 2.0s → **值得捡** ✅
- 错误：2.6s > 2.0s → **不划算** ❌

而且它会连带把"冲刺 vs 全收集收益差"从 +19.1% 压到 +12.7% —— 让我以为关卡调参没调好。（⏳ 这是**当时口径**的读数；2026-09-24 重定基线后 Level1 现值为 **+19.2%**，见 §1.1 的 ⏳ 括注。）

修法：

```csharp
if (cost < e.cost)
{
    e.cost = cost; e.kind = kind;
    // 反向图里那条对应的边**必须一起改**
    for (int j = 0; j < rev[to].Count; j++)
        if (rev[to][j].to == from) { rev[to][j].cost = cost; rev[to][j].kind = kind; }
}
```

自检用例 T6 专门钉死它：把一枚金币放在悬空台上，手算绕路 = `跳上去 0.582 + 掉下来 0.432 + 走路 − 直线 = 1.014s`。如果回程按跳下来计价，算出来会是 1.47s。

> **教训**：任何"派生数据结构"（缓存、索引、反向图）都是 bug 的温床。
> 每次更新主结构时，问一句："还有谁也存了这份数据？"

#### Bug 4：障碍判定逻辑**写反了一半**

求解器有个"逃课检测"：把某个障碍移除后重算最短时间，看变化大不大。

原本的判据：

```csharp
string verdict = delta > 0.4f ? "挡住了一段路 ✅"
               : (delta > 0.05f ? "影响很小 ⚠" : "完全不影响 —— 装饰品 ❌");
```

问题：**它假设移除障碍只会让路线变慢或不变。**

但移除一堵**墙**会让路线变**快**（玩家可以抄近路）！ `delta` 是负的，于是这个真障碍被误判成"装饰品"。

正确判据：

```csharp
// 移除之后变**快**（delta < 0）= 它原本在挡路
// 移除之后变**慢** = 它原本是必经的落脚点
// 两个方向都说明它有用；只有几乎不变才是真的装饰品
if (delta > 0.4f)       verdict = "移除后变慢 → 它是必经的落脚点 ✅";
else if (delta < -0.4f) verdict = "移除后能抄近路 → 它原本挡着路，是真障碍 ✅";
else if (Mathf.Abs(delta) > 0.05f) verdict = "影响很小 ⚠";
else                    verdict = "完全不影响 —— 可以绕过，等于装饰品 ❌";
```

> **教训**：写判据的时候，把每一个分支**逐条念出来**："大于 0.4 表示什么？小于 −0.4 表示什么？"
> 如果某个真实情况落不进任何一个分支（或者落进了错的那个），判据就是错的。
> **两个方向的差异，永远要显式处理。**

### 4.3 无头游戏循环：没有 Play 模式怎么测"运行时行为"

#### 问题

第 4 步要验证机关**联动**。联动是运行时行为 —— 压板要真的被压到、门要真的开关、平台要真的载人。

常规做法是 Unity 的 Play 模式测试。但探针证明：**批处理模式下进不了 Play 模式**（跑了 400 秒没完成）。

#### 解法：自己推帧

```csharp
static void Step(List<MonoBehaviour> scripts, Scene scene, float seconds)
{
    const float dt = 1f / 60f;
    int frames = Mathf.RoundToInt(seconds / dt);
    for (int i = 0; i < frames; i++)
    {
        Physics2D.Simulate(dt);            // ① 真实物理步
        DeliverTriggerEvents(scene);       // ② 补发物理事件
        foreach (var s in scripts) Call(s, "FixedUpdate");   // ③ 反射调生命周期
        foreach (var s in scripts) Call(s, "Update");
        Thread.Sleep(1);
    }
}
```

`Call` 是按名字 + 参数个数反射调用（含私有方法）：

```csharp
static void Call(object target, string name, params object[] args)
{
    foreach (MethodInfo m in target.GetType().GetMethods(Any))
    {
        if (m.Name != name) continue;
        ParameterInfo[] ps = m.GetParameters();
        if (ps.Length != args.Length) continue;
        bool ok = true;
        for (int i = 0; i < ps.Length; i++)
            if (args[i] != null && !ps[i].ParameterType.IsInstanceOfType(args[i])) { ok = false; break; }
        if (!ok) continue;
        m.Invoke(target, args);
        return;
    }
}
```

**用的是真实的游戏脚本、真实的碰撞体、真实的物理**，只是帧由测试来推。

#### 两个必须诚实标注的妥协

| 妥协 | 原因 | 怎么补 |
|---|---|---|
| 编辑模式下 `Awake` / `Start` **不会被调用** | Unity 只在运行时调 | 测试**显式补调一次** |
| 编辑模式下 `Time.time` **不走**、物理回调**不派发** | 主循环不跑 | ① 事件的**真实 Collider** 由测试交给产品的处理函数<br>② 与时间有关的行为（路点等待、松手容差）显式模拟，并在报告里注明 |

第一个妥协特别有教育意义。不补 `Awake` 的话：

- 移动平台的 `_active` 字段停在默认值 `false` → **平台活着但不动**
- 敌人的 `_startX` 停在 `0` → 它以为自己该在 x=3，于是每帧都判定"该转身" → **原地抽搐**

**看起来像机关坏了，其实是测试没搭对。** 如果我不查这一层，就会去改产品代码，把好代码改坏。

而第二个妥协 —— 我没有假装它不存在，而是让测试**自己报告**：

```
· 编辑模式下 Time.time 在 120ms 里前进了 0.000s（不走 → 与时间有关的行为改用显式模拟，报告里会标注）
· 物理回调：编辑模式下 Physics2D.Simulate 不派发 OnTrigger/OnCollision，
·           所以由测试自己做重叠查询、把**真实的 Collider** 交给产品的处理函数。
·           （碰撞矩阵已经单独解码验证过，真实运行时派发没问题。）
```

#### 最终成果

```
========== 机关验收结束：通过 59 项 / 失败 0 项 ==========
```

包括这些**真**断言：

- ① 站到压板 A 上 → 压板被压住 → **门 1 打开** → 人走开后**门 1 仍然开着**（一次性锁定）
- ② 平台 1 沿路线自己走起来了（走了 3.60 格）→ 站上去的玩家被一起带走（玩家移动 3.80 格）→ 玩家确实站在平台面上（没穿下去）
- ③ 敌人自己在巡逻（范围 40.0 ~ 43.2）→ 碰到玩家 → 玩家死亡 → 上报 LevelManager → 可以复活
- ④ 平台在左端时门 2 关着 → **平台扫过高台 → 压住压板 B → 门 2 打开** → 平台离开 → 压板松开 → 门 2 关回去
- ⑤ 玩家经过检查点 → 复活点被改写（2.0,0.5 → 39.0,3.0）

### 4.4 数据管线与它的安全网

#### 管线

```
LevelData（JSON）  ──▶  LevelBuilder.Build()  ──▶  场景
     ▲                                              │
     └──────────── ExportScene() 逐字段读回 ─────────┘
```

#### 三条防线

**防线 1：往返一致性检查**

导出 → 用导出结果重建 → 再导出 → 逐行比对。一致才保存场景。

**防线 2：磁盘 JSON vs 场景导出结果**

这条是**防线 1 抓不到**的（防线 1 只能证明"重建前后自洽"，证明不了"导出器没漏字段"），所以单独加了一条。

**防线 3：CanonicalLines() 规范化行**

比对不是比 JSON 文本（字段顺序、空格、浮点格式都会变），而是比**规范化后的行**，每行一个语义单元：

```
T Ground|Ceiling|476,6|96,6|-
T Ground|Pillar_2|256,2|8,5|-
O Coin|coin_1|coin_1|32,2|0.6,0.6|10|-
L plate_A->gate_1|2|0
```

（格式照 `LevelData.cs:393-420` 的 `CanonicalLines()`：`T {kind}|{name}|{qx},{qy}|{qw},{qh}|{p}`、
`O {kind}|{id}|{name}|{qx},{qy}|{sizeX},{sizeY}|{p}|{pts}`、`L {sourceId}->{targetId}|{mode}|{delay}`。
`kind` 写**枚举名**（`Ground` / `Coin`…），`mode` 写**整数** 0~3（`2` = `CloseOnce`），空数组写 `-`。）

一眼能看懂，diff 出来直接可读。

#### 这条安全网真的救了命

第 4 步回归时它报警了（§3 ⑨ 那段报错）。查下来是 **Level1 的场景和 JSON 漂移了**：

| | 场景 / 现在的 JSON | 之前的 JSON |
|---|---|---|
| 走道上多出一个方块 | `Pillar_2` x 64..66，y 0.5..1.75（贴地悬空 **0.5**，玩家高 1.0 钻不过去） | 没有 |
| 天花板走廊位置 | `Ceiling` x 119..143 | x 118..142 |

其余 24 条地形与设计文档**完全吻合**。

漂移的原因：这条管线假设"数据是真相源，场景由 JSON 重建"。一旦有人在**场景里**直接改东西而没重新导出，两边就会分开走。

**影响评估**：求解器重算后 Level1 的数字**一个都没变**（35.0s / +19.1% / 11 枚值得捡）—— 因为那条路线本来就只是"多跳一下"。但净空检查已经把这个方块标成 ❌。（⏳ 2026-09-24 重定基线后 Level1 现为 **36.8s / +19.2%**；当时"净空只报警、不改路线"，现在净空已经进模型。）

> **可迁移的做法**：双向管线一定要假设"两边都会被人手改"，并且**每次都检查它们是否一致**。
> 不要相信"我们规定只改 JSON"这种纪律 —— 纪律会破，检查不会。

### 4.5 一个数字背后的能力包络

这一条很短，但特别能说明"先算再做"的价值。

从 `PlayerController` 里读出来的真实参数：

```
moveSpeed      = 6.5
jumpHeight     = 3.0
gravityScale   = 3.0  →  重力 = 9.81 × 3 = 29.43
```

推导：

```
上升时间 t1 = √(2 × 3.0 / 29.43) = 0.4515s
落下时间 t2 = √(2 × (3.0 − 高度差) / 29.43)
滞空 = t1 + t2
水平能跨 = 滞空 × 6.5
```

得到的关键数字：

| 场景 | 水平能跨 |
|---|---|
| 同高度跳跃 | **5.87 格** |
| 跳上 1.5 格高 | ~5.0 格 |
| 跳上 2.75 格高（Level1 的柱子） | 3.78 格 |

**Level1 的所有坑宽都是按这个设计的**：

- 断桥 3 格（跳得过去，是节奏不是障碍）
- 深坑 4 格（跳得过去）
- **6 格坑 = 硬约束**（跳不过去，必须走别的路）

第 2 步重做 Level1 时曾把深坑做成 4 格 —— 结果史莱姆必掉坑（`_lastSafePosition = 13.51` 而坑在 16→20）。修法是**把坑从 4 格收窄到 3 格**。这个修改能一次做对，就是因为手里有 5.87 这个数。

## 5. 设计亮点精讲

### 5.1 【最核心】"时间就是钱" —— 一句话让整个游戏可计算

前面 §1 讲过数学。这里讲**设计上为什么这个选择是对的**。

普通平台跳跃游戏有两个分离的评价维度：

- **快**（速通）
- **全**（收集）

玩家经常面对一个**无法比较**的选择："我该走快一点，还是绕路去拿那个东西？"

- 如果金币只是"加分"，那答案是"能拿就拿" —— 没有取舍。
- 如果金币要花很多时间，那答案是"看心情" —— 没有答案。

**这个 demo 把两者换算成同一种货币之后，取舍有了解：**

```
每秒时间价值 = 5 元（= 全局掉钱速度 drainPerSecond）
一枚金币 = 10 元 → 预算 2.0 秒
```

于是每一个决策都变成一个**有明确答案的算术题**：

| 金币 | 绕路代价 | 预算 | 结论 |
|---|---|---|---|
| `C_Pillar1` | 1.3s | 2.0s | 值得捡 ✅ |
| `C_Pillar5` | 1.3s | 2.0s | 值得捡 ✅ |
| `C_Zig3` | 2.3s | 2.0s | **不划算 ❌** |

**这就是这个 demo 区别于普通平台跳跃的地方**：它不是"跳得准"，是"算得清"。

而且这个设计**同时解决了叙事**：你是来**换钱**的，时间拖越久史莱姆越蔫、卖价越低。机制和故事是同一件事。

### 5.2 难度来自"如何收益最大"，不是"能不能过去"

原话：

> 难度主要来自"如何收益最大"，部分关卡难点在唯一路径。

这句话是关卡设计的**方向盘**。

- 如果难度 = "能不能过去"，那难点就是操作精度 → 玩家挫败 → 卡关 → 弃游。
- 如果难度 = "怎么走收益最大"，那难点就是**判断** → 玩家思考 → 试错 → 发现更优解 → **爽**。

而且后者**天然可重复玩**：第一次通关 400 元，第二次 480 元，第三次 506 元 —— 同一条路线，三次不同的满足感。

这个 demo 的求解器报告正好量化了这一点：

```
冲刺（不捡币）  35.0s  →  425 元
全收集（估算）  42.8s  →  506 元
差距 +19.1%
```

**两条路都"能通关"，但赚的钱差 19%。** 这就是"可优化的空间"。

### 5.3 "15%~35%" 这个数字是怎么来的

这是整个项目里我最喜欢的一个设计决定。

**问题**：收益差多大才算好？

- 差 0%（两条路一样赚）→ 玩家没有理由思考 → 设计失败
- 差 100%（全收集的钱是冲刺的两倍）→ 玩家没有理由冲刺 → 也失败
- 差 5% → 玩家感觉不到差别 → 等于 0%
- 差 50% → 全收集变成唯一解 → 也等于没有选择

**答案：15%~35%。** 在这个区间里：

- 差得够多，玩家能感觉到（19% ≈ 80 元，是能看见的差别）
- 差得不够多，两条路都合理（想冲就冲，想捡就捡）
- 存在一个"更好的答案"，但不是"唯一答案"

有了这个数，关卡就有了**可验收的健康指标**：

| 关卡 | 冲刺 | 全收集 | 收益差 | 判定 |
|---|---|---|---|---|
| Level0 | 697 元 | 834 元 | **+19.7%** | ✅ |
| Level1 | 425 元 | 506 元 | **+19.1%** | ✅ |
| Level2 | 417 元 | 498 元 | **+19.4%** | ✅ |

> ⚠ **口径更新（2026-09-23）**：收益差的分子已从"全收集"改为 **R\*（精确最优）**，当时三关变为 **+20.4% / +19.5% / +20.6%**。
> 本表（含上面那个代码块）保留的是**当时口径**的历史数字 —— 最新定义见 `定案_收益公式与调参基准.md` §10，最新数值见 `项目进度_现状与下一步.md` §5。
> ⏳ **再更新（2026-09-24 重定基线）**：净空进模型后四关现值 **+18.2% / +19.2% / +16.3% / +18.0%**；四关"冲刺 / 全收集（精确，可行解）/ `R*`"金额为 **692 / 818 / 818**、**416 / 496 / 496**、**412 / 479 / 479**、**556 / 656 / 656** 元（来源：2026-09-24 `BatchSolveAll` 实测）。
> ⏳ **再更新（一次判据修正后）**：Level3 的冲刺售价 556 → **560 元**（最短时间 8.7 → **8.1 秒**）；四关金额现为 692 / 818 / 818、416 / 496 / 496、412 / 479 / 479、**560 / 656 / 656** 元。

**四关全部落在区间内，而且彼此接近。**（⚠ Level2 的 **+16.3%** 已贴近 15% 下限 —— 后续调参照 `定案_收益公式与调参基准.md` §10.5。）这说明关卡设计是**有刻度**的，不是凭感觉摆的。

> **可迁移的做法**：任何一个"要有取舍"的系统，都要有一个**数值化的健康区间**。
> "我觉得这样差不多" 不是设计，"这个值应该在 15~35 之间" 才是。
> 有了区间，你才能一眼看出哪一关不对，也才能让另一个人接手调参。

### 5.4 强制力总表：对"设计意图"的诚实审查

这是这个项目在**设计纪律**上最值得学的一招。

对于玩家能做的每一个动作，列出它**能不能硬性地强迫玩家做某件事**：

| 动作 | 能硬强制什么 | 结论 |
|---|---|---|
| 抓 | 水（软强制 —— 不抓会掉血，但不会死） | 软 |
| 扔 | **几何上不硬** —— 空手跳 5.87 格 > 扔的射程 4.76 格 | **不能硬强制** |
| 引导石 | 1.0 格矮通道（硬 —— 史莱姆自己过不去） | **硬** |
| 哨子停留 | 半（能定住，但玩家也能自己站那儿） | 半 |
| 放下 | **不可硬强制** —— 史莱姆自己会跳 3.0 格高 | **不能硬强制** |

**为什么这张表值钱**：它逼你把"我以为玩家必须这么做"变成"玩家**真的**必须这么做吗"。

真实案例：设计上想让玩家"必须把史莱姆放下才能过某个地方"。但一算 —— 史莱姆自己的跳高是 3.0 格，玩家能过去的地方它多半也能过去。**所以"放下"这个动作在几何上强制不了。**

发现之后有两条路：要么改设计（换一个真正的硬约束），要么接受它是软的。但**不能假装它是硬的** —— 否则做出来的关卡，玩家会直接绕过去，而你还在奇怪为什么没人用那个机制。

> **可迁移的做法**：给每个机制列一张"强制力表"。
> 对每一格，问："我能不能构造一个场景，让玩家**非用这个动作不可**？"
> 答不上来的格子，就是设计里的漏洞，不是你没想到而已。

### 5.5 "呆呆史莱姆"：把负担做成主角

设计上很聪明的一点：**你要护送的不是宝物，是一个笨蛋。**

传统护送任务里，NPC 是"会动的任务物品"。这个 demo 里的史莱姆：

- 自己会走，但**走得笨**（`isStuckNow` 判据：在追你 + 距离超过跟进距离 + 这一步几乎没动）
- 卡住时会**挣扎**：抖动、压扁、蹦哒、喘气、变红
- 被抱着的时候**免疫伤害**（碰撞矩阵 + 代码双重保证）
- 掉进水里会掉血，掉太多就死，**整关失败**

**"挣扎"这个动画是设计上最妙的一笔。** 它把"我的同伴卡住了"这件本来很烦的事，变成了**可爱的、值得同情的、你会想回去救它的**一件事。

而且它顺手解决了一个纯技术问题：玩家永远知道史莱姆卡在哪。不需要 UI 箭头、不需要文字提示。

**这个动画的调试过程也很值得看**（四层 bug 叠在一起）：

1. `MoveTowards` 在 `distance <= stopDistance` 时提前返回 → 卡住检测根本没跑
2. `spriteRoot` / `spriteRenderer` 在预制体里是 null → 而且 `UpdateWobble` / `UpdateFlash` 里判空了就直接 return → **蠕动、闪红、举着晃动、玩家转身全部静默失效**
3. 蓄力计时器被闪烁的条件反复重置 → 永远蓄不满
4. `IsStrandedBelowPlayer` 在正常的跟随跳里会误报，在卡在墙角时又漏报（因为 `IsGrounded = false`）

最终解法：把判据收成一条极简的

```csharp
IsStuckNow(movedThisStep) = 在追你 && 距离 > 跟进距离 + 0.6 && 这一步移动 < 0.03
```

再加上一个 `_stuckness` 蓄力计（避免瞬间抖动就触发）。

> **教训**：一个"没生效"的表现层 bug，往往不是一个 bug，是**四层叠在一起**。
> 修第一层之后看起来还是没好，很容易误判成"方向错了"。
> 正确的做法是：**先确认每一层单独能不能动**（在 sprite 上打个日志），再往上叠。

### 5.6 无文字教学

教学关（`Level0`）的设计目标：**不用一行文字，教会 6 个动词**。

手段是**象形图路牌**（`Mural` 结构，占位文字 `showMuralLabels`，正式版换成图形）：

- 图形在左、动作在右（或反过来），像机场指示牌
- 玩家看到"跳跃的简笔画"就自然会跳
- **不打断、不弹窗、不需要点"确定"**

为什么这个决定重要：这个游戏的机制核心是**取舍**，不是操作。如果教学关要先读 300 字说明，玩家在理解机制之前就流失了。

而且它和 §5.1 的设计是配套的：**如果你要玩家算账，你得先让他愿意留下来。**

## 6. 事故档案

每个坑一行，附教训。这是全文最该反复看的部分。

| # | 事故 | 表现 | 根因 | 教训 |
|---|---|---|---|---|
| 1 | `Rigidbody2D.linearVelocity` | 编译不过 | 这是 Unity 6 的 API，2022.3 用 `velocity` | **版本差异先查文档，别凭记忆** |
| 2 | 字段初始化器里调 `LayerMask.GetMask` | Unity 抛异常 → **后面所有字段初始化都不跑** → `ClearLevel` 空引用 | 静态 API 不能用在字段初始化器 | 初始化放 `Reset()` / `Awake()` |
| 3 | MonoBehaviour 序列化字段**覆盖**代码默认值 | 改了代码默认值没生效 | Unity 序列化优先 | **数值要写进 LevelData，不能只写在组件上** |
| 4 | 尺寸/出生点被吸附到 1/4 格 | 手感变了（终点 2×2 → 1.6×1.6，出生 y 0.6 → 0.5） | 把"技术值"当"设计值"量化了 | **尺寸和出生点是世界浮点，不是网格整数** |
| 5 | `Mathf.Lerp` 参数顺序写反 + 没 `Clamp01` | 通关越快奖励越低 | | 加一张**自检表**（2 求解与校验 → 收益公式自检）把它抓出来 |
| 6 | 导出器漏读字段（3 次：`murals` / `parTime` / `levelIndex`） | **静默**：用默认值填上，一切"正常" | 双向转换的经典陷阱 | **磁盘 JSON vs 场景导出**逐行比对 |
| 7 | `SuggestValue` 里有一句永不可达的 `if (n == "levelindex" && v == 0) return 1;` | 当时没影响 | 埋雷 | **删掉。**"现在不会触发"不是保留死代码的理由 |
| 8 | 场景名硬编码 + 无条件解锁下一关 | `Scene 'Level3' couldn't be loaded` | | 从 Build Settings 自动发现 + `CanStreamedLevelBeLoaded` 守卫 |
| 9 | 深坑 4 格 | 史莱姆**必掉坑** | 4 格是能跳的，但史莱姆的跟随逻辑不行 | 坑宽收到 **3 格** |
| 10 | 相机边界语义搞错 | 玩家在井里**看不见** | `ClampToBounds` 会用 `orthographicSize` 内缩，所以 `boundsMin` 是**取景框**不是相机中心范围 | 改 `camMinY = -11`、`camMaxY = 16` |
| 11 | 玩家"不能跳跃" | 排查了很久 | 第一假设（站在史莱姆上）被**解码碰撞矩阵**推翻 | **假设要用数据推翻，不要用推理推翻** |
| 12 | 修第 11 条的第一版无效 | `if (groundLayer.value == 0)` 永远不成立 | 修的是错的分支 | 修 bug 后要**验证修复真的生效**（加日志） |
| 13 | 挣扎动画看不见（四层叠加） | 修一层还是没好 | 见 §5.5 | **分层验证，不要整块猜** |
| 14 | 求解器第一代 | 报 7.0s（下界 24.0s） | 段内走路免费 | **模型粒度决定结果对错** |
| 15 | 求解器第二代 | 报"不可达" | 起跳绑死在端点 | 修 bug 别推向另一个极端 |
| 16 | 求解器：掉落按跳计价 | 报出"爬柱子再跳进井里"的**荒谬但合理**的路线 | `continue` 短路 | **每个 `continue` 都是一个需要证明的断言** |
| 17 | 求解器：墙不存在 | 抽掉台阶后依然"可达" | 合并走道时没切断 | 模型要包含**障碍**，不只是**表面** |
| 18 | 求解器：反向图不同步 | 柱顶金币绕路**正好翻倍** → 改变设计结论 | `Add` 只更新了正向图 | **派生结构必须同步更新** |
| 19 | 求解器：障碍判定写反一半 | 真墙被当成装饰品 | 只考虑了 `delta > 0` | **两个方向的差异必须显式处理** |
| 20 | 净空检查判据用 `<` 而不是 `<=` | 净空恰好等于身高的矮通道**漏掉了** | 边界情况 | **边界值要专门测一次** |
| 21 | 移动平台路点挂成平台子物体 | 平台**一路飞出去停不下来**（本该停 x33，飞到 x43 还在跑） | 路点跟着平台一起移动，永远追不上 | **"相对坐标"和"世界坐标"要时刻分清** |
| 22 | 压力板默认掩码漏掉 `MovingPlatform` | "平台压板"**永远触发不了** | 代码注释的意图 ≠ 掩码的现实 | **注释描述意图，配置决定现实** |
| 23 | 无头测试里没补调 `Awake` | 平台"活着但不动"、敌人"原地抽搐"，**看起来像机关坏了** | 编辑模式不调用运行时生命周期 | **先确认是测试的问题还是产品的问题** |
| 24 | Level1 场景与 JSON 漂移 | 多出一个 `Pillar_2`（贴地悬空 0.5）、天花板偏 1 格 | 有人在场景里直接改而没重新导出 | 双向管线要**每次都检查一致性** |

## 7. 工具箱：命令速查

### 7.1 无头跑 Unity（这是这个项目效率的基石）

```powershell
# 关键：Windows 上必须用 Start-Process -Wait
# 用 & 调用 GUI 子系统的 exe 不会等它结束
$p = Start-Process -FilePath '<Unity 安装目录>\Editor\Unity.exe' `
     -ArgumentList '-batchmode','-quit','-projectPath','<工程路径>', `
                   '-executeMethod','<类名>.<方法名>','-logFile','<日志路径>' `
     -PassThru
$p.WaitForExit(500000)
$p.ExitCode
```

**三个必须知道的坑**：

1. `&` 不会等待 → 用 `Start-Process -Wait` / `-PassThru` + `WaitForExit`
2. 残留的无窗口 Unity 子进程会**占住工程锁** → 每次调用之间 `Get-Process Unity | Stop-Process -Force`
3. 要跑真实帧（不 `-quit`）时靠 `EditorApplication.Exit(code)` 自己结束

### 7.4 文件同步纪律

这个项目有**两份拷贝**：

```
<工作副本>\              ← 我的工作区（编辑在这里）
CarrySlimeToCash\        ← 工程根目录
```

同步方式：`Copy-Item` + **MD5 校验**。

```powershell
$a = (Get-FileHash $src).Hash
$b = (Get-FileHash $dst).Hash
Write-Host "match=$($a -eq $b)"
```

**为什么要校验**：因为"我以为我拷过去了"和"我真的拷过去了"是两件事。一次静默的拷贝失败，会让你调试一个**根本不存在的 bug**。

## 8. 如果重来一次，我会怎么做

### 会保留的

1. **第一原则**：先找到"让这个系统可计算"的那个设计决定（这里是"时间就是钱"）。
2. **数据是真相源**：JSON → 场景，而不是场景 → JSON。
3. **每一层都配体检仪**：下界自检、手算用例、逐动作明细、净空检查。
4. **风险优先**：没跑过的代码先跑。
5. **验收标准先写**：写成能被证伪的现象。
6. **回归基线**：改之前记下"应该还是什么样"。

### 会做得更早的

1. **求解器应该更早做。** 它是第 3 步，但它的价值在第 2 步（重做 Level1）就该体现出来。如果先有求解器再设计关卡，Level1 的收益差第一版就能落在 15%~35%，不用来回调。
2. **"净空"应该从第一版就进模型。** 现在它是报告里的一个警告段 —— 但一个"看不见头顶"的模型，在平台跳跃游戏里是**结构性缺陷**，不是可以后补的功能。
3. **碰撞矩阵应该第一天就解码存档。** 我是在排查"玩家不能跳跃"时才去解的。`门 ↔ 地面 = 关`这种冷知识，早一天知道就少一次误判。
4. **回归清单应该第一天就有。** §7.3 那张表是事后总结的，但它其实可以一开始就写下来。

### 会改掉的

1. **`continue` 少用。** 求解器那个"掉落按跳计价"的 bug 就是 `continue` 造成的。现在我的习惯是：每个 `continue` 旁边都写一句"为什么剩下的情况不可能更好"。
2. **派生结构一开始就用同一个对象。** 反向图不同步的 bug，本可以靠"正反向共享同一个 `Edge` 引用"从结构上避免。
3. **报告里的每一句判断，都要标注它的适用范围。** 求解器现在会明说"我看不见头顶" —— 但这个习惯应该从第一个报告就开始有。
