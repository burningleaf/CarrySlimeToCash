```
                    ┌──────────────────────┐
                    │  LevelData (唯一真相源) │
                    └───────────┬──────────┘
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
      Editor 面板         游戏内编辑器        LevelSolver
   （造官方关卡）      （玩家自制地图）    （校验 / 评分）
              │                 │                 │
              └────────► LevelBuilder ◄───────────┘
                              │
                              ▼
                       Unity 场景（运行时对象）
```

求解器只写一次，两边都用。官方关与玩家地图同格式 → 玩家地图天然可被校验、可试玩、可进关卡列表。

## 1. 分层与职责

关卡在设计上分三层，**机关和几何不是"另一种谜题"，而是给路径优化加约束的东西**。

| 层 | 内容 | 对玩家 | 对设计者 |
|---|---|---|---|
| **路径层（核心）** | 引导石 + 地形 + 金币 + 时间 | 要解的优化题 | 要构造的带权图 |
| **机关层** | 压力板 / 门 / 移动平台 | 会改写题面的变量 | 时间相关图的边 |
| **几何层** | 墙、坑、台阶、隧道、水 | 静态约束 | 节点 / 边 |

## 2. LevelData 格式

### 2.1 坐标约定

- 世界 1 格 = 1 Unity 单位 = 1 屏幕瓦片基准。
- **存储坐标 = 1/4 格整数（quarter unit, `q`）**：`world = q × 0.25`。
  - 用整数避免浮点漂移，JSON 友好。
  - 注意：0.25 的整数倍**只能表达 0.25/0.5/0.75…**，1.1 和 1.8 都落不到网格上，所以这两个设计值必须改（见 §4.3、§4.4）。
- **地形块 `TerrainBlock`**：`qx/qy` = 矩形**左下角**，`qw/qh` = 尺寸。
  以**矩形**存储（非单格瓦片）：编辑器用画笔刷小格，保存时**贪心合并成矩形**，数据量小、求解器好算。
- **物件 `LevelObject`**：`qx/qy` = **中心**（1/4 格整数），`sizeX/sizeY` = 尺寸（**世界浮点**，0 = 用该类的默认尺寸）。
  尺寸不吸附网格，理由见下。
  两套轴的取向不同是有意的：地形要算"可站立顶面"，左下角最直观；物件跟随 Unity 的中心轴心。
- 只有尺寸真正参与玩法的物件（`Gate`、`MovingPlatform`）才记录尺寸；金币之类写 0，
  免得 0.9 这种非整格直径被量化成 1.0 反而改变了碰撞体。

### 2.2 结构总表

```csharp
// 全部为普通 [System.Serializable] 类，不用 ScriptableObject
LevelData
├─ meta            关卡元信息
├─ terrain[]       地形矩形块
├─ objects[]       物件（金币/石头/机关/敌人/检查点）
├─ links[]         机关联动关系
└─ murals[]        无文字壁画提示
```

**meta**

| 字段 | 类型 | 说明 | 备注 |
|---|---|---|---|
| `levelId` | string | 唯一 id | 存档与关卡列表用 |
| `displayName` | string | 显示名 | 仅 UI 显示，不参与玩法 |
| `basePrice` | float | 基础价 | 收益公式第一项 |
| `maxHp` | float | 满血量 | 默认 100 |
| `timeLimit` | float | 软时限（秒） | 时间奖励曲线的参考点 |
| `timeBonusMode` | enum | `Linear` / `Step` / `None` | 见 §6.3 未决项 U1 |
| `timeBonusA` `timeBonusB` | float | 曲线参数 | 不写死，可调 |
| `startStones` | int | 开局给几颗引导石 | D1 的核心旋钮 |
| `playerSpawn` | int2 (q) | 玩家出生 | 由场景模板里的玩家位置导出 |
| `slimeSpawn` | int2 (q) | 史莱姆出生 | 同上 |
| `bonusSteps` | float[] | 阶梯时间奖励 | 每两个数一组 `[时间上限, 倍率]`，按时间升序 |
| `coinValue` | int | 默认金币面值 | 物件没写 p[0] 时用 |

> 终点不再放 meta，而是 `objects[]` 里 `kind = Goal` 的一个物件——统一处理，少一条特例。

**terrain[] — 地形矩形块**

| 字段 | 类型 | 说明 |
|---|---|---|
| `qx` `qy` `qw` `qh` | int | 1/4 格单位的左下角与尺寸 |
| `kind` | enum | `Ground` / `OneWayPlatform` / `Water` / `Hazard` / `Decor` |
| `spriteIndex` | int | 外观（0 = 用 kind 默认） |

> `Ground` 同时代表"地面"和"墙"——求解器只看几何，不看名字，所以不单列 `Wall`。
> 尖刺并入 `Hazard`，壁画并入 `murals[]`，都不单列。

**objects[] — 物件**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | **关卡内唯一**，`links` 靠它引用（替代 `FindObjectOfType`） |
| `kind` | enum | `Coin` / `SlimeOrb` / `Waypoint`(引导石) / `Goal` / `PressurePlate` / `MovingPlatform` / `Gate` / `Checkpoint` / `Enemy` |
| `qx` `qy` | int | 位置 |
| `qx` `qy` | int | 中心（1/4 格整数） |
| `sizeX` `sizeY` | float | 尺寸（**世界浮点**；0 = 用该类默认尺寸） |
| `p` | float[] | 物件私有参数：移动平台的行程与周期、门的开关延时、金币面值…… |

**links[] — 机关联动**（这是"拖动链接"的数据形态）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sourceId` | string | 触发者（压力板 / 敌人死亡 / 检查点） |
| `targetId` | string | 被触发者（门 / 移动平台 / 桥） |
| `mode` | enum | `Toggle` / `OpenOnce` / `CloseOnce` / `Reverse` |
| `delay` | float | 延时秒 |

> 关键：`links` 是**显式数据**，所以"压力板 → 门"这条关系可以被求解器读到并参与计算，而不需要运行时反查。这也顺手满足了"禁止 `FindObjectOfType` 跨模块查找"。

**murals[]** — 无文字教学壁画：`{ qx, qy, muralId }`，`muralId` 指向美术资源。仅表现层，不参与求解。

## 3. 能力模型（求解器的物理内核）

所有数值必须从脚本字段读取，**不写死**。

### 3.1 参数来源

| 参数 | 来源 | 当前值 |
|---|---|---|
| `jumpHeight` / `carryJumpHeight` | `PlayerController` | 3.0 / 1.8 |
| `gravityScale` | `PlayerController` | 3 |
| `moveSpeed` / `carryMoveSpeed` | `PlayerController` | 6.5 / 3.5 |
| `jumpCutMultiplier` | `PlayerController` | **0.65**（原 0.5：轻点只跳 0.75 格，和按满差 4 倍，手感忽大忽小） |
| `minJumpHoldTime` | `PlayerController` | **0.08**（新增：起跳后这段时间内不截断上升速度） |
| `maxFallSpeed` | `PlayerController` | **18**（原 25：每物理步走 0.5 格，落点会漂） |
| `coyoteTime` | `PlayerController` | 0.1 |
| `grabRadius` | `PlayerGrab` | 1.2 |
| `placeOffsetX` / `placeOffsetY` | `PlayerGrab` | 0.8 / 0.1 |
| `throwForceForward` / `throwForceUp` | `PlayerGrab` | 7 / 10 |
| `followSpeed` | `SlimeController` | 6.5 |
| `thrownRestTime` | `SlimeController` | 1.5 |
| `waypointYOffset` | `PlayerGrab` | 0.5 |

重力 `g = 9.81 × gravityScale = 29.43`。

### 3.2 推导公式

跳跃实现是 `v = sqrt(2·g·h)`，故**顶点高度恰好等于 `jumpHeight`**。

| 量 | 公式 | 空手 | 携带 |
|---|---|---|---|
| 最大跳高 | `h` | 3.00 | 1.80 |
| 最小跳高（跳跃中断） | `h × 0.5²` | 0.75 | 0.45 |
| 同高滞空 | `2·sqrt(2h/g)` | 0.903 s | 0.700 s |
| 同高水平距离 | `滞空 × 速度` | 5.87 | 2.45 |

扔（`v = (7, 10)`，史莱姆 `gravityScale = 3`）：

- 上升顶点 `= 10²/(2×29.43) = 1.70 格`
- 同高滞空 `= 2×10/29.43 = 0.680 s` → 射程 `= 7 × 0.680 = 4.76 格`
- 落地后 **1.5 s 硬直**（口哨可打断）→ 这是收益模型里的**真实时间成本**

### 3.3 落点包络（以站在 y=0 平地为基准）

玩家碰撞体 `0.8 × 1.2`（脚本口径）→ 站立时中心 y = 0.6；携带跳顶点时中心 y = 2.4。

| 动作 | 施放点 y | 史莱姆中心最高 y | **可落台面顶** |
|---|---|---|---|
| 放下 | 玩家中心 + 0.1 | 2.50 | **2.05** |
| 站着扔 | 玩家中心 + 0.5 = 1.10 | 2.80 | **2.35** |
| 跳起后扔 | 玩家中心 + 0.5 = 2.90 | 4.60 | **4.15** |

（"可落台面顶" = 史莱姆中心最高 − 半高 0.45）

## 4. ⚠️ 实测发现的两处数值冲突

> 这两处正是"校验需求集中在能否通关"的活证据。**动手做任何关卡内容前必须先修。**

### 4.1 `Plat_1 = 2.5` 用"放下"永远够不着

- 教学意图是教"**放下**" → 上限 **2.05**，2.5 差 0.45 格，是死局。
- 站着"扔" → 上限 2.35，仍然不够。
- 只有"**跳起来再扔**"（上限 4.15）才够——但那是进阶操作，教程关第一节不该教它。

**建议**：`Plat_1` 改为 **1.8 ~ 2.0**（与"放下"这个动词匹配）。
若坚持 2.5，则必须在旁边放一个 ≥ 0.7 高的中间台阶，或把教学意图改成"跳起来扔"。

### 4.2 碰撞体尺寸：脚本口径 ≠ 磁盘 prefab 口径

| 口径 | 玩家碰撞体 | 史莱姆碰撞体 | 玩家高 | 史莱姆高 |
|---|---|---|---|---|
| **脚本**（`SlimeDemoSetup.cs:352/371`） | `Box 0.8×1.2` | `Circle r=0.45` | 1.2 | 0.9 |
| **磁盘 prefab**（`Scenes/Player.prefab` / `Slime.prefab`） | `Box 1×1` | `Circle r=0.5` | 1.0 | 1.0 |

后果（对隧道机制是致命的）：

- 脚本口径 + 净空 1.1 → 史莱姆余 0.2、玩家差 0.1 → **隧道只放史莱姆，机制成立** ✅
- 磁盘口径 + 净空 1.1 → 两者都是 1.0 高 → **玩家也能过，机制失效** ❌

**建议**：以脚本口径为准（1.2 / 0.9），并重跑 `★ 一键全部构建` 让 prefab 与脚本一致。

### 4.3 隧道净空 1.1 → 建议改为 1.0

网格化要求净空取 0.25 的整数倍（§2.1），而在脚本口径下成立区间是 `(0.9, 1.2)`：其中唯一的 0.25 倍数是 **1.0**。

- 1.0 → 史莱姆余 0.1、玩家差 0.2 → 机制成立 ✅
- 1.25 → 玩家（1.2）也能过 → 机制失效 ❌

**建议净空 = 1.0**（顺带把原先"只剩 0.05 余量"的紧绷感解掉）。

### 4.4 附带发现（工程卫生）

- `Player.prefab` / `Slime.prefab` / `Ground_A|B|Pit.prefab` 全部生成在 `Assets/_Project/Scenes/`，而 `Assets/_Project/Prefabs/` 是空的（只有 5 个空子目录 meta）。应当挪到 `Prefabs/`。
- `Assets/_Project/Scenes/SampleScene.unity` 是残留，可删。

### 4.5 「放下」无法用高度强制 —— 机制强制力总表

`SlimeController.JumpFollow` 是这样写的：**玩家一跳，史莱姆就按"滞空时间相等"反算高度跟着跳**（`h = g·t²/8`）。玩家空手跳 3.0，史莱姆重力与玩家相同，所以**史莱姆自主跳跃高度也≈3.0**。

推论：**任何"台子有多高"都无法强制玩家使用"放下"**——史莱姆自己跳得上去。原先教程关打算用 `Plat_1 = 2.5` 来教"放下"，这个前提不成立。

| 机制 | 能否被几何硬强制 | 靠什么强制 |
|---|---|---|
| **抓** | ✅ | 水（史莱姆进水掉血 → 软成本，但有效） |
| **扔** | ✅ 硬 | 4 格宽的坑（携带跳只能跨 2.45） |
| **引导石** | ✅ 硬 | 1.0 净空隧道（玩家高 1.2 进不去） |
| **哨子·停留** | ⚠️ 半 | 需要史莱姆留在原地时（例如踩压力板） |
| **放下** | ❌ | 只能"软强制"：史莱姆跟随时会乱跳，先放下再探路是自然策略 |
| **哨子·召回** | ❌ | 任何"按住才算"的板子会困住史莱姆；任何"自锁"板子又让停留失去意义 |

**结论**：教程关里 `Plat_1` 的作用应当改写成"**让玩家顺手用一次放下**"（软教学），而不是"不通关就逼你用放下"。要硬强制一个动词，只能用**几何**（宽度、净空、危险区），不能用高度。

## 5. 求解器设计（Editor 侧）

### 5.1 为什么不能靠人眼

核心玩法是路径规划 + 收益最大化：路线数与收益差异是组合问题，人眼花 1 小时也数不清"禁用这颗石头后还能不能通"。而这件事有确定的算法。

### 5.2 算法：时间分层动态规划（**目标规格**，不是 A\*）

> **实现状态：当前实现是玩家层站点图 + Dijkstra（含 R\* 掩码枚举）。本节描述的"时间分层 DP + 三层图（玩家/史莱姆/耦合）"尚未实现。**
> 也就是说：**本节是目标规格，不是现状**。现状见 `项目进度_现状与下一步.md` §5.5；R\* 的精确口径见 `定案_收益公式与调参基准.md` §10。

因为**时间只会前进**，把"时间"作为一层展开后得到的图是**无环的（DAG）**，可以直接按时间层做 DP，无需 A*、无需优先队列。

```
状态 S = (层 layer, 节点 node, 时刻 t)
         layer ∈ { 玩家层, 史莱姆层, 耦合层 }
         node  = 一个"可站立面段"（由 terrain 矩形块推导）
         t     = 0 … timeLimit，步长 dt = 0.05 s

转移（按 t 递增逐层推进）：
  等待 / 走到相邻段 / 跳（Δy 在能力区间 [h_min, h_max] 内，水平量随 h 变化）
  / 抓 / 放下 / 扔 / 吹口哨（召回 or 停留）/ 随移动平台移动
  机关按 t 决定门开闭与平台位置
  经过金币 → 加收益；经过危险 → 扣血；到达终点 → 结算

输出：R* = max_t 结算收益，并回溯出最优路线
```

**为什么是三层图而不是 `(玩家位置 × 史莱姆位置)` 联合状态**：联合状态是 `O(N²)`（≈ 200² = 4 万）× 携带 2 × 时间 1200 层 = **近亿状态，不可行**。

三层图把交互（抓/放/扔/口哨）抽成**层间耦合边**，只在"两者同段或距离 ≤ `grabRadius`"时存在，于是 `|S| = 3N`（≈ 600）× 时间层 → **秒级可解**。

若某些关卡必须精确联合（例如史莱姆会自己掉进坑），退化为 `(player, slime)` 联合 DP，但**限制史莱姆只能在其所在连通区内**，实际组合数远小于 `N²`。

### 5.3 五个校验指标

> 实现状态（2026-09-23，以 `Editor/LevelSolver.cs` 为准）：**M1 / M4 已实现**（玩家层）；**M2 部分实现（保守上界，非精确）**；**M3 / M5 未实现**；**R\* 收益（掩码枚举，精确最优）已实现**，作为收益差的分子（口径见 §5.2 的状态行与 `定案` §10）。
> ⚠ **M2 不要当成"精确已实现"**：现值是**逐枚绕路相加的保守上界**，**精确的全收集最短时间要真做一遍"金币必须全拿"的 DP 才有**（见下表 M2 行）。

| # | 指标 | 算法（**目标规格**） | 用途 | 实现状态（**现状**，以代码为准） |
|---|---|---|---|---|
| M1 | **冲刺最短时间**（不捡币） | DP，金币权重置 0 | 执行向量化 | ✅ **已实现**：玩家层站点图上"不捡币的最短路"就是它 |
| M2 | **全收集最短时间** | DP，金币必须全拿 | 上限参考 | 🟡 **部分实现 / 保守上界（非精确）**：`allCollectTime = minTime + Σ(可达金币的绕路)` —— **保守上界，不是精确联合最优**（`LevelSolver.cs:747-750`；`定案` §10.2 第 2 条）。**现值是上界；精确值需真做"金币必须全拿"的全收集 DP** |
| M3 | **收益前沿** | λ-sweep：对 `收益 = 钱 − λ×时间` 跑多组 λ，取 Pareto 集 | 判断是否有规划深度 | ⬜ **未实现** |
| M4 | **逃课检测（反事实）** | 禁用一条交互边（拿走石头 / 关掉平台）后重跑，仍能通关 → 该机制是装饰品 | 保证"没有逃课" | 🟡 **已实现（几何版，只对地形有效）**：移除一块地形后重跑，判"是不是必经障碍"（`LevelSolver.cs:1267-1268` 自注"只看玩家走位；机制层检测要等史莱姆层"）。**机关不进模型** —— 求解器只读 `data.terrain`（`:1275`）+ `Goal`（`:627`）/ `Coin`（`:632`），**从不读** `links` / 门 / 压板 / 平台 / 检查点 / 敌人 |
| M5 | **引导石下限** | 对 `startStones = k` 二分搜索，找最小可行 k | 衡量路径深度 | ⬜ **未实现**（要史莱姆层） |
| **R\*** | **最优收益**（收益差的分子） | 金币**掩码枚举**（`MaxMaskCoins = 16`）× 每个掩码的多源 Dijkstra × `price(t)` 带 `Clamp01` | 判断规划深度 / 收益差口径 | ✅ **已实现，且是精确最优**：`ComputeBestScore`（`LevelSolver.cs:823-940`）；口径见 `定案` §10 |

> ⚠ 现在输出的 R\* 是**单点最优**，不是 §5.3 M3 要的**收益前沿（Pareto 集）** —— 两者别混。

### 5.4 "解谜精彩"的可操作判据

- `R*` 与直觉/贪心路线收益 `R̄` 的差距：
  - `R* ≈ R̄` → **假选择**，没有规划深度（收集物是装饰品）
  - 差距 ≥ 35% 但最优解唯一且反直觉 → **猜谜**，不是解谜（阈值与实现一致：`gap > 35`；定义见 `定案_收益公式与调参基准.md` §10）
  - 理想：**2~4 条路线收益接近但不相等，且代价各不相同**（时间 / 血量 / 石头）
- 执行向关卡反过来：M1 的最优路线必须**唯一**，且 M5 恰好等于给的石头数。

### 5.5 两层校验（第二层不可省）

| 层 | 形式 | 速度 | 回答 |
|---|---|---|---|
| 一期 | **玩家层站点图 + Dijkstra**（**现状**；"时间分层 DP"是 §5.2 的目标规格，未实现） | 毫秒~秒 | 能不能通 / 最短多长 / 有没有逃课（**只对地形有效**）/ R\* 最优收益；石头下限 M5 未实现 |
| 二期 | **机器人试玩**：把一条路线用虚拟输入真跑一遍，物理是真的 | 慢，定稿时跑一次 | 真实物理下能不能通、卡在第几秒 |

求解器用的是**简化物理模型**，模型错了它会撒谎。所以必须有二期做交叉验证——`Plat_1 = 2.5` 这类 bug 就是靠它兜住的。

### 6.2 即时反馈的边界（重要，遵守原规则）

### 13.4 三条踩坑记录（都是真踩出来的）

**坑 1 —— `LayerMask.GetMask` / `NameToLayer` 不能在字段初始化器或构造函数里调用。**
Unity 会抛 `NameToLayer is not allowed to be called from a MonoBehaviour constructor (or instance field initializer)`。
后果很隐蔽：构造函数抛异常 → **排在它后面的字段初始化器全都没执行** → `List`/`Dictionary` 字段为 null →
下一句 `ClearLevel()` 空引用 → 批处理中止。
正确做法：字段声明留空，在 `Reset()`（编辑器 AddComponent 时自动调用）和 `Awake()` 里补。

**坑 2 —— MonoBehaviour 的序列化字段会盖掉代码里的默认值。**
`LevelBuilder` 的外观参数（`KindStyle`）是序列化在**场景文件**里的。把代码里 `goal.size` 从 1.6 改成 2.0，
**对已经存在的组件毫无影响**——它读的是场景里存的 1.6。所以"改代码默认值"这条路对既有场景无效，
必须改数据（JSON）或写一个"重置为代码默认值"的工具。
→ 这也是把物件尺寸放进 `LevelData` 的直接理由：**能进数据的就别留在组件上**。

**坑 3 —— 物件的"尺寸"是技术值，不是设计值，不该吸附网格。**
最初只给 `Gate`/`MovingPlatform` 记录尺寸，其余物件重建时回落到默认值——
结果 Goal 的触发区从 2×2 悄悄缩成 1.6×1.6（缩小 20%），**会改变通关判定**。
出生点 y 同理（0.6 被量化成 0.5 会把角色塞进地面 0.1）。
最终规则：**位置吸附 1/4 格；尺寸与出生点用世界浮点。**
