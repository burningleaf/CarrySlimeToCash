# 带呆呆史莱姆越障换钱

一个平台跳跃游戏，加一套配套的关卡数值验证工具链。单人开发，Unity 2022.3 + URP 2D。

做这个不是为了做游戏，是为了解决一个具体问题：**"这关设计得好不好"到底是主观判断，还是能算出来的数字。**

求解器目前**只建模玩家层**：史莱姆跟随、引导石约束、收益前沿（M3）都还没进模型。

### 两条刻意的设计约束

1. **不用 `CharacterController2D`、不用任何付费插件** —— 角色控制、抓取、投掷、跟随/寻路全部自己写。
2. **禁止攀爬 / A\* / NavMesh / 传送** —— 所以"关卡能不能过、哪条路最快"**没有现成库可用**，只能自己造工具（也就是下面那套求解器）。

史莱姆的"寻路"也被设计成**玩法机制**（玩家放引导石路点，史莱姆沿路点走），不是算法导航。

### 程序化美术：视觉质量也能机器验收

**20 张教学象形图壁画全部由代码程序化生成像素图**（不是手绘 + 导入，PPU 统一 40）。

一次用户反馈"元素互相重叠看不清" ⇒ 定位根因（键帽半径设成 11 ⇒ 直径 22px = **画布面积的 34.4%**）⇒ 立**分区 + 硬规则**（含"不许靠把元素画小来解决拥挤"）+ **写盘前的机器可验防重叠自检** ⇒ **20/20 一次全过**。

并做了**独立像素复核**：把磁盘上真实的 PNG 与"用同一套画法在内存里渲染出来的图"**逐像素比对，差异 = 0**。

### 三条边界（我知道自己的模型哪里不精确）

1. **求解器对机关是"盲"的** —— 门 / 压板 / 移动平台 / 敌人**不进模型**。所以我从不拿"可达 ✅"当作"这关能过"的证明。
2. **角色精灵还没接上**（当前玩家是白方块）—— 所以别问美术完成度。
3. **有一个已知的保守近似**：某类下落跳的可行性判定偏保守，求解器报的时间比真人能做到的略大一点。

## 核心模型：时间 = 金钱

史莱姆会随时间掉血，**血条同时就是售价条**——血量直接决定最终能卖多少钱。

满格售价由 parTime 决定：**满格售价 = 10 × parTime 元**；**血条 = 2 × parTime 点**，每点固定 **5 元**。

| parTime | 血条点数 | 满格售价 | 1 点血 | 掉血速率 |
|---|---|---|---|---|
| 50（Level2） | 100 点 | 500 元 | 5 元 | 1.0 点/秒 |
| 60（Level1 / Level3） | 120 点 | 600 元 | 5 元 | 1.0 点/秒 |
| 80（Level0） | 160 点 | 800 元 | 5 元 | 1.0 点/秒 |

注意：**每点血恒 5 元、掉血恒 1.0 点/秒**（两个都是全局常数，与 parTime 无关）—— 关卡长短只决定**血条有多少点**；所以「每秒掉 5 元」是真的每秒 5 元，也就是 **1 点 = 1 秒 = 5 元**。

金币面值 10 元，所以：

```
10 元 ÷ 5 元/秒 = 2.0 秒
```

**一枚金币，正好够买史莱姆 2 秒的耐心。** 绕路 1.3 秒能到 → 值；绕路 2.6 秒 → 不值。

这样"跳还是不跳"就从一个手感问题，变成一道能算的题。

设计意图是让史莱姆从直觉上的"拖累"变成玩法的核心：所以它绑定了关卡收益，时间惩罚直接打在它的血条上。玩家看着血条掉，就能直观判断这枚金币值不值得绕。

### 为什么是 5 元/秒

两个约束：

1. **数值区间**：每秒时间价值要落在 3~5 元/秒。太小的话时间压力是假的，金币的绕路预算会大到失去意义。
2. **整数化**：关卡的 `parTime` 只要求取 10 的倍数，所有对外可见的数就都是整数：

```
1 秒 = 5 元 = 半枚金币的绕路预算
```

没有小数，玩家能心算，不用查表。

### 关卡经济规模只由一个参数决定

满格售价和掉血速率都是从 `parTime` 推出来的，不需要逐关手调：

```
满格售价 = 10 × parTime（= 2 × parTime 点 × 5 元/点）        掉血 = 1.0 点/秒（与 parTime 无关）
```

所以**设计者每关只需要定一个数：`parTime`**。四关实测：80 / 60 / 50 / 60 秒，对应满格售价 800 / 600 / 500 / 600 元。

### 三个口径

求解器给三种走法的结算收益：

- **冲刺**：走最短路径，**一枚金币都不捡**。跑得最快，血条剩得最多，但只有售价
- **贪心全拿 R̄**：把所有金币的绕路时间加起来，金币全算。**这不是一条可行路线**——它把玩家根本拿不到的金币也算进了分子，只用来当"不思考的玩家"的对照
- **最优解 R\***：枚举"捡哪些金币"的所有组合，取结算收益最大的那个

```
收益差 = (R* ÷ 冲刺总分) − 1，分母是冲刺总分
```

Level1 实测：冲刺 **416 元** / 全收集（精确，可行解）**496 元** / 最优解 R\* **496 元** → 收益差 **+19.2%**。

它衡量的是：**绕路收集相对于完全不绕路，能多赚多少。**

分母取"冲刺"而不是"关卡资源总额"，是因为满格血量和全部金币不可能同时拿到，那样算出来的数没有决策含义；而"冲刺"是一个真实玩家能达成的结果。

拆开看：

```
收益差 = (收集到的金币 − 因绕路损失的血量价值) ÷ 冲刺总分
```

因为收集越多耗时越长、售价越低，但金币越多。收益差为正，意味着**绕路拿到的金币大于掉血损失的钱**。

**为什么用 R\* 而不是"全收集"**：单枚金币的取舍和"联合最优"不是一回事。Level1 有 12 枚金币，按单枚往返成本判定只有 11 枚"值得捡"，但最优解实际上全拿了——因为顺路捡多枚时，边际成本远低于单枚往返成本（`C_Zig3` 单枚绕路 2.3 秒 > 预算 2.0 秒，但在最优路线里边际只多 0.8 秒）。用"全收集"当分子会掩盖这一点。

## 验收判据：15% ~ 35%

两个方向的失效点先定下来：

| 收益差 | 玩家实际体验 |
|---|---|
| < 10% | 收集要素是装饰品，没动机绕路 |
| **15% ~ 35%** | **会纠结，但不被强迫** |
| > 40% | 不捡就过不去，变成猜谜 |

健康区间取 **15% ~ 35%**，即两个失效点内侧。落在这里，代表"金币值得收集，但不碾压冲刺路线"。

**要说清楚：这是设计目标，不是实测结论。** 它的作用是把"这关好不好"从主观判断变成可验收的数字。这个区间还没有经过真实玩家测试校准。

## 数据

| 关卡 | 最短时间 | 冲刺 | 最优解 R\* | 收益差 |
|---|---|---|---|---|
| Level0（教程关） | 21.6s | 692 元 | **818 元** | **+18.2%** |
| Level1 | 36.8s | 416 元 | **496 元** | **+19.2%** |
| Level2 | 17.7s | 412 元 | **479 元** | **+16.3%** |
| Level3 | 8.1s | 560 元 | **656 元** | **+17.1%** |

四关全部落在 15%~35% 区间内。

- **最短时间**：玩家跑完这关的最短耗时，求解器算的
- **直线下界**：水平距离 ÷ 移速。任何走法都不可能比它更快，用来防"求解器算错"。Level1 是最短通关 36.8s、下界 30.3s
- Level1 的图规模：**22 段可站立面 / 72 站点 / 188 条边**（四关范围：11~22 段 / 29~72 站点 / 86~188 边）

> ⚠️ **一个已知边界**：`R* ≥ R̄` 只在**所有金币都可达**时成立。Level3 有拿不到的金币，于是出现例外（R\* 656 < R̄ 676）——因为 R̄ 把这些拿不到的币也算进了分子。这说明用"贪心全拿"当指标会在边界条件下失真。

## 工具链

四个 Unity Editor 工具，入口都在 `Tools/呆呆史莱姆/` 菜单下。

**关卡求解器** — `Editor/LevelSolver.cs`

把关卡抽象成"站点图"。节点不是格子，是每段可站立面上的若干站点：段两端、出生点、终点、每枚金币的位置，以及与所有邻段的最近点。段内相邻站点连"走"边，按距离计费；跨段连"跳"边。

用 Dijkstra 正反向各跑一次，**几毫秒**出结果：

- 正向：起点到每个节点的最短时间
- 反向：在反向图上从终点出发 = 每个节点到终点要多久
- 两者相加，才算出**单枚金币的绕路代价**（绕去拿它再奔终点，比直奔多花几秒）

输出最短时间、金币取舍、逃课检测，以及三种结算口径。**R\*** 用掩码枚举求：枚举"捡哪些金币"的所有组合（上限 16 枚），每个组合求一次最短路，取结算收益最大的那个。因为对固定组合金币总额是常量、而售价随耗时单调不增，所以同一组合内"时间最短"必然"得分最高"——枚举就是全局最优，不是估算。

**求解器自检** — 菜单 `◇◇-1`

**67 项断言，分 14 组（T1~T14）**。下表是其中最关键的几组 —— T1~T6 是答案能手算的迷你关卡，T7 之后覆盖 R\* 最优性、平跳跨距、携带态、头顶楼板等：

| 用例 | 内容 | 手算答案 |
|---|---|---|
| T1 | 一条 18 格的直路，移速 6.5 | 耗时必然是 18 ÷ 6.5 |
| T2 | 一个四格宽的坑 | 跳得过去；耗时 = 前段 + 跳跃 + 后段 |
| T3 | 一个六格宽的坑 | 空手最远跳 5.87 格 → 应该报"过不去" |
| T4 | 借台阶翻 5 格高墙 | 抽掉台阶后应报"翻不过去" |
| T5 | 两枚金币：一枚顺路、一枚绕 8 秒 | 顺路的值得捡，绕 8 秒的不划算 |
| T6 | 悬空台上的金币 | 回程要按**掉落**计价，不是按跳跃 |
| T7 | R\* 的最优性 | 只捡划算的那枚，且收益 ≥ 冲刺、≥ 贪心全拿 |
| T8~T14 | R\* 联合最优 / 平跳跨距上限 / 携带态跳跃 / 头顶楼板与下落路径 / 净空检查等 | 每条都是**预先手算好的期望值** |

**机关联动验收** — `Editor/MechTest.cs`

不开 Play 模式，用反射驱动真实脚本跑机关联动，**59 项断言**。命令行运行，不用打开 Unity：

```
Unity.exe -batchmode -quit -projectPath <工程路径> -executeMethod MechTest.BatchMechTest
```

**数据管线** — `Editor/LevelDataWindow.cs`

场景导出成 JSON、JSON 重建回场景、还有一步往返一致性检查（导出 → 重建 → 再导出）。

关卡数据因此变成纯文本，能 diff、能 grep、能进 Git。同一个 Level1，场景文件约 361 KB、JSON 只有约 9 KB —— 差 40 倍，而能进版本管理的正是后者。往返检查是用来证明管线没坏的，不靠人肉比对。

## 踩过的坑

求解器的自检抓出 **4 个 bug**，共同特征是**结果看起来合理，但其实是错的**。

| 现象 | 真正原因 |
|---|---|
| 一条 92 格长的地面被当成瞬移，Level1 报出 7.0 秒（直线下界 24.0 秒） | 建图时把整段当一个节点，段内走路没计费 |
| 报出"先爬柱子再跳进井里"这种荒谬路线 | 掉落按"跳"计价时用了 continue 短路，漏连了一条更便宜的边 |
| 某处"可以直接落到地面"的边根本不成立 | 下落途中半空有平台，人会落在上面 |
| 移动平台把玩家带到 x43（本该停在 x33） | 路点挂在平台的子物体上，位置跟着缩放漂移 |

还有一个更隐蔽的：**反向图的边没跟着更新**，导致金币绕路代价正好翻倍（1.3s 变成 2.6s），把收益差从 +19.1% 压到 +12.7%，看起来像关卡没调好。

### 站点图改了三次

**第一代**：一个可站立面 = 一个节点。最直觉的做法，结果是段内走路免费——一条 92 格长的地面等于瞬移，Level1 报出 7.0 秒。

**第二代**：每段取两端两个节点，段内走路收费。但起跳被绑死在端点上，竖井里嵌在坑底的台阶（dx=0 的垂直跳）永远连不上，求解器报"不可达"。

**第三代**：每段上取若干站点。段内相邻站点连"走"边，跨段连"跳"边，并且"与所有其他段的最近点"也要成为站点。前两代的问题都解决了，还顺带能算出金币的绕路代价。另外加新平台时站点会自动出现在对的位置，不用手写死。

### 无头测试的两个妥协

测试跑在编辑模式下，有两个问题必须说明：

- **`Awake` / `Start` 不会被调用**（Unity 只在运行时调）。测试里显式补调一次。不补的话，移动平台的 `_active` 停在 `false`（平台活着但不动），敌人的 `_startX` 停在 `0`（每帧判定该转身，原地抽搐）——看起来像机关坏了，其实是测试没搭对。
- **`Time.time` 不走、物理回调不派发**。由测试自己做重叠查询，把真实 Collider 交给产品的处理函数；与时间有关的行为（路点等待、松手容差）显式模拟，并在报告里注明。
