# 带呆呆史莱姆越障换钱 · 关卡数值验证工具链

> 用「时间=金钱」模型，把平台跳跃关卡从「靠手感判断」变成**可计算、可验收**的设计问题。

| 核心数据 | |
| --- | --- |
| **经济模型** | 「时间=金钱」：金币 = **10 元/枚** → 每枚金币取舍预算 = **2.0 秒** |
| **验收判据** | 冲刺 vs 全收集收益差落在 **15% ~ 35%** |
| **实测结果** | Level0 **+19.7%**、Level1 **+19.1%**、Level2 **+19.4%** —— 三关**全部达标** |
| **求解器** | Level1 图规模 **19~20 段 / 74~78 站点 / 196~201 条边**，Dijkstra 正反向各一次，**几毫秒**出结果 |
| **自检** | 求解器自检 **15 项**（6 个答案能手算的迷你关卡）→ 抓出 **4 个 bug** |
| **联动验收** | 机关联动断言 **59 项全过**（命令行无头运行） |
| **数据管线** | Level1：JSON **9.2 KB** ↔ 场景 **364 KB**，可 diff、可 grep、可往返一致性检查 |
| **环境** | Unity **2022.3.62f3c1** + URP 2D |

## 1. 设计问题

平台跳跃游戏的「金币该不该捡」和「难度曲线合不合适」，长期只有一个判断方式：**设计师的手感**。这带来三个具体麻烦：

1. **无法证伪** —— 说一条路线"值得走"是主观判断，没人能反驳，也没人能确认。
2. **无法回归** —— 改一个跳跃高度或金币位置，整关体验是否还成立，只能重新试玩一遍。
3. **无法沟通** —— 和程序、美术讨论"这里要不要放金币"时，拿不出依据。

而这个项目是**单人开发、没有美术资源**的：所有素材都是纯色占位块。
所以核心乐趣**不能依赖画面表现**，必须能在美术进来之前就被证明成立。

**结论：我要做的不是一款游戏，而是一套能把设计判断变成数字、并且能自动验证这套数字没算错的方法。**

---

## 2. 核心模型：时间 = 金钱

**把金币的获取成本，统一折算成时间。**

- 玩家绕路去拿一枚金币，付出的真实成本是**时间**，不是"难度"。
- 因此定义核心参数：**每枚金币的取舍预算 = 2.0 秒**
  —— 一枚金币（面值 10 元）带来的收益，必须至少抵得上玩家为它多花的 2.0 秒。
- 于是「跳还是不跳」从一个手感问题，变成一个**可计算的决策**。

模型输出三个可比较的量：

| 量 | 含义 |
| --- | --- |
| **冲刺收益** | 走最短路径、完全不刻意收集时的收益 |
| **全收集收益** | 遍历全部可达金币时的收益（以及多付出的时间） |
| **收益差** | 全收集相对冲刺的收益提升比例 —— **这就是难度曲线的体检指标** |

---

## 3. 判据：15% ~ 35% 是怎么来的

这是整个项目里唯一需要设计师拍板的数字，所以必须说清依据：

| 收益差 | 玩家的实际体验 |
| --- | --- |
| **< 10%** | 收集要素是**装饰品**，玩家没有动机绕路，关卡没有规划深度 |
| **15% ~ 35%** | 玩家**会纠结**该不该绕路 —— 有规划深度，但不强迫 |
| **> 40%** | 变成**猜谜**：不收集就过不去，路线选择失去意义 |

**答案：15% ~ 35%。** 落在这个区间，代表"金币值得收集，但不会碾压冲刺路线"。

> ⚠️ **诚实的边界**：这个区间是**基于设计假设设定的目标**，尚未经过真实玩家测试校准。
> 它的价值在于把"这关好不好"变成**可验收的数字**，而不是声称这个数字有实证依据。

## 4. 实测结果

| 关卡 | 最短时间 | 直线下界 | 冲刺 | 全收集 | **收益差** | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| Level0（教程关） | 20.5s | 19.4s | 697 元 | 834 元 | **+19.7%** | ✅ 落在 15%~35% |
| Level1 | 35.0s | 30.3s | 425 元 | 506 元 | **+19.1%** | ✅ 落在 15%~35% |
| Level2 | 16.6s | 13.4s | 417 元 | 498 元 | **+19.4%** | ✅ 落在 15%~35% |

**三关收益差稳定在 +19.1% ~ +19.7%，全部落在预设健康区间内。**

- **最短时间**：玩家跑完该关的最短耗时（求解器给出）
- **直线下界**：水平距离 ÷ 移速，**任何走法都不可能比它更快** —— 用来防"求解器算错"
- Level1 求解器还算出：**11 枚金币值得捡**（其余绕路不划算）

另有两条交叉验证：

- 「冲刺 vs 全收集」的收益差，与**手玩实测**结论一致。
- 受伤扣血按**关卡经济规模自动缩放**：撞一下扣 15% 血量。在总收益 458 元的关卡里等于 69 元，在 333 元的关卡里等于 50 元 —— **相对惩罚始终一致，不需要逐关调伤害数值**。

## 5. 工具链：一套 Unity Editor 工具，不是几段脚本

全部入口在 Unity 菜单 `Tools/呆呆史莱姆/` 下，共 **39 个工具**。核心四类：

### 5.1 关卡求解器 —— 回答「这条路线是不是最优的」

`Assets/_Project/Editor/LevelSolver.cs`

- **禁止使用网格寻路**，改为把"可站立面"抽象成**站点图**：
  - 节点 = 每段上的若干**站点**（段两端 + 出生点 / 终点 / 每枚金币的 x + 与所有邻段的"最接近点"）
  - 段内相邻站点连"走"边，费用 = Δx ÷ 移速（**段内走路要收费**）
  - 跨段连"跳"边，费用 = 跳跃耗时
- **Dijkstra 跑两次**（正向一次、反向一次），几毫秒出结果
- 输出：可达性、最短时间、**金币取舍**（哪些金币值得捡）、**逃课检测**、收益差

**为什么用站点而不是"每段一个节点"或"每段两端两个节点"** —— 见 §6 的 bug 案例，这是踩出来的。

### 5.2 求解器自检 —— 回答「求解器本身算错了吗」

菜单：`Tools/呆呆史莱姆/◇◇-1 求解器自检（对答案，改完求解器必跑）`

**15 项断言**，其中包含 **6 个"答案能手算"的迷你关卡**，把结果钉死。
详见 §6。

### 5.3 无头机关联动验收 —— 回答「改了数值会不会崩」

`Assets/_Project/Editor/MechTest.cs`（`MechTest.BatchMechTest`）

- **在不开 Play 模式的情况下**，用反射驱动真实运行时脚本，跑完整机关联动
- 直接用命令行运行，**不需要打开 Unity**：
  ```
  Unity.exe -batchmode -quit -projectPath <工程路径> -executeMethod MechTest.BatchMechTest
  ```
- **59 项断言全过**：压力板 → 移动平台 → 门、敌人、检查点等五类机关的状态流转与组合交互
- 价值：改一个数值后，一条命令验证全部机关行为**没有回归**

### 5.4 数据管线 —— 回答「设计数据怎么进版本管理」

`Assets/_Project/Editor/LevelDataWindow.cs`

| 菜单 | 作用 |
| --- | --- |
| `⓪-1 导出当前场景 → LevelData JSON` | 场景 → 纯文本 |
| `⓪-2 从 LevelData JSON 重建关卡` | 纯文本 → 场景 |
| `⓪-3 往返一致性检查（导出→重建→再导出）` | **证明管线无损** |
| `⓪-5 收益公式自检（打出数值表）` | 数值自检 |
| `◇ 关卡数据编辑器（表格改数值，不碰文本）` | 策划友好的改数入口 |

**价值**：关卡数据是**纯文本、可 diff、可 grep、可生成**，能进 Git，能看见"这次改了什么"。
`⓪-3 往返一致性检查`让"管线没坏"这件事**可自证**，而不是靠人肉比对。

### 5.5 串起来的效果

> 验证周期从 **「反复试玩」** 缩短为 **「点一次菜单（数值）或跑一条命令（机关回归），几毫秒出报告」**。

## 6. 我怎么知道它没算错

> 数值工具最大的风险不是算不出来，而是**算出一个看起来对的结果**。

因此求解器内置 **15 项自检**，专门检查"结果是否自相矛盾"，并据此抓出 **4 个"看着合理但是错的"bug**。

### 6.1 四个 bug（全部由自检抓出）

| # | 现象 | 为什么"看着合理" | 真正原因 |
| --- | --- | --- | --- |
| 1 | 一条 92 格长的地面被当成**瞬移**，报出 Level1 只要 **7.0 秒**（直线下界是 24.0 秒） | 路线本身能走通，数字也不像异常 | 第一代建图把**整段当成一个节点**，段内走路算 0 秒 |
| 2 | 报出"**先爬柱子再跳进井里**"的荒谬但合理的路线 | 每一步跳跃在几何上都成立 | 掉落按"跳"计价时用了 `continue` 短路，**漏连了另一条更便宜的边** |
| 3 | 某处"**可以直接落到地面**"的边根本不成立 | 几何上确实是一条向下的直线 | 下落途中**半空有平台**，人会落在上面 —— 这条边不该存在 |
| 4 | 移动平台把玩家**带到 x43**（本该停在 x33） | 视觉上看平台确实走到位了 | 路点挂在平台的**子物体**上，位置跟着缩放漂移 |

### 6.2 重点案例：站点图的两次失败（bug #1 的完整经过）

**第一代：一个可站立面 = 一个节点。**
最直觉的做法 —— 把地面、平台、台阶都变成节点，能互相跳过去就连边。
→ **段内走路变成免费**。一条 92 格长的地面等于瞬移，求解器报出 **7.0 秒**，而直线下界是 **24.0 秒**。

**第二代：一个可站立面 = 两端两个节点。**
修法很自然：段内走路要收费，所以给每段取两端两个节点，段内连一条"走"边。
→ 起跳被**绑死在端点**上，竖井里嵌在坑底的台阶（dx=0 的垂直跳）**永远连不上**，求解器报"不可达"。

**第三代（最终）：站点法。**
每一段上取若干**站点**，而不是固定取端点：

- 段内：相邻站点之间连"走"边，费用 = Δx ÷ 移速（**段内走路要花钱** ✅）
- 跨段：站点之间连"跳"边
- 关键一条：**与所有其他段的"最接近点"也要成为站点**

→ 两个问题都解决，而且顺带能算出"**金币绕路代价**"。
→ 还带来一个额外好处：**加一个新平台，站点会自动出现在正确的位置**，不需要手写死。

**我学到的**：
> 每一个 `continue`、每一条"看起来显然成立"的边，都是一个**需要被证明的断言**。
> 自检的价值不在于发现 bug，而在于**让 bug 无法伪装成正确答案**。

### 6.3 已知妥协（诚实标注）

无头测试跑在编辑模式下，有两个必须说清的妥协：

| 妥协 | 原因 | 怎么补 |
| --- | --- | --- |
| 编辑模式下 `Awake` / `Start` **不会被调用** | Unity 只在运行时调 | 测试**显式补调一次** |
| 编辑模式下 `Time.time` **不走**、物理回调**不派发** | 主循环不跑 | ① 由测试自己做重叠查询，把**真实 Collider** 交给产品的处理函数<br>② 与时间有关的行为（路点等待、松手容差）显式模拟，并在报告里注明 |

**第一个妥协特别有教育意义**：不补 `Awake` 的话 ——

- 移动平台的 `_active` 字段停在默认值 `false` → **平台活着但不动**
- 敌人的 `_startX` 停在 `0` → 它以为自己该在 x=3，于是每帧判定"该转身" → **原地抽搐**

→ **看起来像机关坏了，其实是测试没搭对。** 如果不去查这一层，就会去改产品代码，把好代码改坏。

第二个妥协我没有假装它不存在，而是让**测试自己报告**出来。

另外：石头下限、史莱姆（敌人）层的求解**尚未实现**，当前求解器只覆盖玩家层。

## 7. 如何运行

**环境**：Unity **2022.3.62f3c1**（2D URP）

1. 用 Unity 打开本仓库根目录（首次打开会自动重建 `Library/`，需要几分钟）
2. 打开场景 `Assets/_Project/Scenes/Level1.unity`
3. 依次执行以下步骤，即可复现本文所有数据：

| 步骤 | 操作 | 预期输出 |
| --- | --- | --- |
| 1 | 菜单 `Tools/呆呆史莱姆/◇◇ 求解当前关卡` | 最短时间 **35.0s** / 直线下界 **30.3s** / 收益差 **+19.1%** / **11 枚金币值得捡** |
| 2 | 菜单 `Tools/呆呆史莱姆/◇◇-1 求解器自检` | **15 项全过** |
| 3 | 菜单 `Tools/呆呆史莱姆/▷ 建机关测试关 LevelMech` | 生成机关测试关 |
| 4 | 命令行（无需打开 Unity）：<br>`Unity.exe -batchmode -quit -projectPath <工程路径> -executeMethod MechTest.BatchMechTest` | 机关联动 **59 项全过** |
| 5 | 菜单 `Tools/呆呆史莱姆/⓪-3 往返一致性检查` | 导出 → 重建 → 再导出，**数据一致** |

> 第 1 步就是全项目的核心：**几毫秒**得到一份可验收的关卡数值报告。

## 8. 局限与下一步

- **健康区间未经玩家实测校准**：15%~35% 目前是设计假设。下一步接入真实玩家通关数据，用实际行为反推金币预算，替代假设值。
- **求解器只覆盖玩家层**：石头下限、史莱姆（敌人）层尚未建模。
- **美术全部是占位色块**：这是刻意的 —— 目的是先证明"不依赖美术表现，核心乐趣也成立"。
- **无头测试有两个编辑模式妥协**：见 §6.3，已在测试报告中显式标注。
